# Implementation phases

The MVP is delivered in fifteen sequential phases. At the end of every phase `verify` passes and production on `nekotype.pages.dev` is deployable. P3–P7 were reordered on Nov 6, 2026, when learning became the core of the product ([ADR 058](../adr/058-learning-first.md)). On Nov 19, 2026, after P5, the typing trainer was removed from the plan and P6–P12 replaced the former P6 (audio) and P7 (release) ([ADR 093](../adr/093-learning-only-words-in-learning.md)). On Nov 21, 2026, after P6, a learning home (P8) and more learning methods (P9) were added, and the later phases moved by two ([ADR 099](../adr/099-learning-home-methods-and-phases-after-p6.md)). Only the next phase is specified in full; a later phase is a scope line until the phase before it closes.

1. **P0 — Monorepo and hygiene.**
   - pnpm workspaces; the baseline `src/` moves to `apps/web`; the engine and kana tables move to `packages/engine` with the table passed via `createEngine`; guards and the `Clock`/`Scheduler`/`Rng` types move to `packages/shared`.
   - Fix the D20 defects, bring documentation and CI in line with D21, update the budget script.
   - **Acceptance:** all baseline tests pass (106 unit, 8 e2e); behaviour is unchanged except for the D20 fixes, each covered by a new test; `packages/engine` has no imports; deployment to the Pages project `nekotype` succeeds and production is served at `nekotype.pages.dev`.
2. **P1 — Engine.**
   - Stream matching with prompt boundaries, `extend()`, rules D2–D8 and D22, attribution D10, flag D11, `compact()`, `view()` with the display-position rule, `errorTarget()`, `committedPrompts()`, `committedTimings()`, `spellingsFor()`, `canonicalFor()`, recording of "expected kana → typed character" pairs, removal of `shouldAbsorb`.
   - **Acceptance:** every input of the accepted-input and rejected-input tables is a golden test; boundary tests cover ん → n, ん → vowel, ん → skip token, っ at a boundary; `packages/engine` coverage ≥ 95%; property tests pass, including the invariant that relaxed accepts every input strict accepts; compact() keeps indices valid over a 1,000-prompt zen stream; all baseline words and phrases compile.
3. **P2 — Input and training screen.**
   - Design-system foundation (tokens, fonts, logo, favicon; ADR 031, ADR 032), hybrid input source, layout and IME notices, text stream, romaji buffer, render-free hot path, `createSession`, keyboard table, zen finish, idle prefetch, font preload, all strings moved to i18n, dependency-free router with route stubs and `_redirects` entries, the slice layout and view separation from "UI architecture".
   - **Acceptance:** session and input logic is tested without rendering; render test shows 0 renders per keystroke and ≤ 1 on prompt completion; keystroke work p95 ≤ 8 ms and keystroke → next frame p95 ≤ 2 frames; e2e (b) from the baseline passes (typing with focus on a button); IME notice not shown for latin composition; device-matrix pass for input on Android (Gboard) and iOS (deferred to the P7 device-matrix pass when P2 was closed, 2026-11-06).
4. **P3 — Learning.**
   - IndexedDB: the database `nekotype` with the stores P3 uses (`settings`, `delta`, `meta`), and the reset on a changed `SCHEMA_VERSION` ([ADR 061](../adr/061-schema-reset-before-release.md)); later phases add their stores by raising `SCHEMA_VERSION`. Nothing is migrated: `kanaflow:settings:v1` is deleted at the first start, and `showTranslation` becomes a required field. The typing screen reads and writes its settings in IndexedDB; `kanaflow:progress:v1` stays in localStorage, read by the typing screen as in P2, until P4.
   - Learning on `/` ([Learning](learning.md)): tracks, unlocking with dependencies, learning sessions (introduction, recall, recognition with the distractor rules and the visually-similar table, focus and weighted task choice), the answer time with K, confidence, boxes and review sessions, the session summary, the kana chart with its states, the mastered count and the streak, learning settings, `learn` counters, the learning section of `/stats`. "Reset progress" also clears the learning state.
   - Typing moves to `/type` as a lazy route and keeps its P2 behaviour otherwise. The `/learn` stub and its route are removed, with no redirect. Content `single`, the row selection and the fallback kana pool are removed; the latency test runs Words and Phrases.
   - The input source moves to `shared`. `AudioProvider` is injected into the learning session with a provider that plays nothing, called after every task.
   - Design system version 10 ([ADR 059](../adr/059-design-system-v10.md)): `KanaTask` with `createTaskController` for learning tasks; `shared/ui` takes the design's names (`Toggle` → `Switch` with the label and description on the left, button variant `ghost` → `text`), drops the line under `Nav` and under the `Dialog` title, writes `en / ru` in lower case, and the loading notice no longer blinks; key hints use `+` and `→`; "Show the romaji" on touch screens, in recall and on `/type`; the config bar folded on a phone; a prompt wider than a line breaks between tokens ([ADR 060](../adr/060-long-prompt-breaks-between-tokens.md)).
   - Fonts: the glyphs listed under "Glyphs to add to subsets" in the [design decisions](../design/source/decisions.md) are added to the subsets ([ADR 034](../adr/034-design-tokens-and-font-build.md)): `·` in JetBrains Mono 400; `⌘` in JetBrains Mono 400; `−` (U+2212) in JetBrains Mono 400 and 500 and Golos Text 400; U+00A0 and U+202F in Golos Text and JetBrains Mono, 400 and 500. Each font stays within its budget.
   - **Acceptance:**
     - property tests with a seeded `Rng`, a fake `Clock` and a simulated learner whose answers come from a seeded model, on both tracks: kana unlock one at a time and only when every unlocked kana is confident; no kana unlocks before its dependencies are confident (ヴ unlocks before ヴァ and ヴィ); the unlocked set never shrinks; っ, ー, small kana, ゐ and ゑ never appear; answers in one track never change the other; the same seed gives the same sessions;
     - task choice with a fixed `Rng` over 10,000 draws: a kana is chosen no less often when its median answer time or its error count grows; kana in focus get 50% ± 2% of the tasks while kana out of focus exist; recognition gets 1/3 ± 2% of the tasks; the same kana never comes twice in a row when another is available;
     - answer time on fixed keystroke times: with K = 200 ms, あ typed at 800 ms and し typed at 800, 1000 and 1200 ms both give 800 ms, and き typed at 300 and 1100 ms gives 900 ms; the result never falls below the time of the first accepted key; K changes from 200 ms to the median of the last 50 intervals at the 20th interval; intervals across a rejected key or Esc are left out; an answer's own intervals do not change its time;
     - confidence at its boundaries: with the default target a median of 1500 ms is confident and 1501 ms is not; 9 correct answers of 10 are confident and 8 are not; 9 answers are never confident; a changed target applies at once;
     - boxes with a fake `Clock` in a fixed time zone: the first confidence moves a kana to box 1, due the next local day; promotion and demotion by reviews; learning-session answers never change the box of a kana in box 1 or higher; due dates across a daylight-saving change;
     - streak: one answer makes a day active, while an introduction or a typing test alone does not; the local midnight boundary; a missed day resets the current streak and keeps the best one;
     - the session summary on fixed answer sequences; every recognition task has 4 options in every state of both tracks, starting with the vowels; no distractor shares a spelling with the answer in either strictness;
     - a learning session leaves the typing statistics unchanged and a typing test leaves the learning state unchanged; a recall keystroke causes 0 renders and the answer at most 1; no IndexedDB write happens inside a keystroke handler;
     - schema reset: a database with another `meta.schemaVersion`, a missing store or an unreadable `meta` is deleted and created again, and the application starts with default settings without an exception; a failing open leaves the application running from memory with the notice and the legacy keys kept; the first start deletes `kanaflow:settings:v1` and leaves `nekotype:locale` and `kanaflow:progress:v1`;
     - e2e: a full learning session by keyboard (typing and keys 1–4) on Chromium and by tap on WebKit, ending on the summary; a test on `/type`; the deploy smoke test sees `/type` answer 200 with the application and `/learn` answer 404;
     - the budgets pass with learning in the initial chunk and typing as a lazy route chunk.
   - **Closed** on 2026-11-09 at commit e023577, after the design review of the build ([ADR 062](../adr/062-design-review-of-the-p3-build.md), PRs 81–87) and the fixes of the issues found after the phase ([ADR 063](../adr/063-unconfident-kana-in-focus.md), PRs 88–93).
5. **P4 — Words and phrases.**
   - Content: transcription parser written against the pinned export, then the pipeline, N5–N4 words from the pinned JLPT mapping with homonym merging, 300–500 verified phrases with per-sentence author data, build report, Russian coverage report, `/about` page with source licences and the generated phrase credit list, "Source" link on the typing screen.
   - Typing: KPM and kana accuracy, `TestResult`, test-end rules including idle end and a hidden tab, statistics applied with the saved result (D23), `KanaStat` for word weights, deletion of `kanaflow:progress:v1` at the first start (nothing is migrated), client-side decay, counters, the `results` and `records` stores, the results screen with the difference to the average and to the personal best, "Repeat" and the repeat mark, local history and the typing section of `/stats`, personal-best badge.
   - **Acceptance:** build is reproducible from pinned sources; compile failures ≤ 5% of the selected items per source ([Content](content.md), "Exclusion threshold"); an audit of 50 randomly sampled phrases finds at most one reading error; every phrase has a Tatoeba id and author usernames and appears in the credit list; chunks ≤ 40 KB; font within budget; the first start deletes `kanaflow:progress:v1`; metrics verified on fixed event sequences; idle end verified with a fake `Clock` and `Scheduler`: 5 seconds without input ends a time or count test, zen is exempt, `endedAt` is the last keystroke, and the result gives no personal best; a restart leaves statistics unchanged except `started`; personal-best rule and key covered by tests; the average checked with 0, 1, 10 and 12 earlier results of a key, a repeat left out of it; a repeat replays the same prompts, is saved with `repeated` = true and gives no personal best; `delta` stays one record after 1,000 simulated tests; a typing test leaves the learning state unchanged; lazy chunks within budget.
   - **Closed** on 2026-11-12 at commit d1ad3a7 (PRs 99–112). The word source is the pinned JLPT mapping, 1,275 words; 500 phrases; no compile failure in either source; the audit of 50 phrases found no reading error (PR 101).

   - **Order of work.** The data model of `user_stats` is checked against the 10 ms CPU limit before anything depends on it ([ADR 078](../adr/078-user-stats-targeted-updates.md)):
     1. Measurement on Cloudflare: a minimal Pages Function on a test project applies a batch to a year-long `user_stats` row by ADR 078; CPU time from `wrangler pages deployment tail` in a cold and a warm isolate, `rows_read` and `rows_written` from D1's `meta`. A result over the limit amends ADR 078 before step 5. Done: the measurement failed ([ADR 081](../adr/081-sync-measurement-p5.md)) and [ADR 082](../adr/082-sync-acknowledgement-without-snapshot.md) amended the model and the pass line.
     2. Functions and D1 scaffold: Hono, `_routes.json`, migrations, local development with `wrangler pages dev` and the Vite proxy.
     3. OAuth and sessions.
     4. Merge and patch functions in `shared/runtime` with their property and equivalence tests.
     5. `/api/sync`.
     6. The client sync engine: `snapshot`, `outbox`, batches, the Web Lock, failed requests.
     7. Guest merge, sign-in, sign-out and the expired session; the account section of `/settings`.
     8. Server history.
     9. Account deletion.
     10. Report action with Turnstile and `/api/reports`.
     11. The acceptance measurements: repeated on Cloudflare at the end of the phase ([research note](../research/2026-11-19-p5-acceptance.md)).
   - **Initial chunk.** The initial JS had 3.7 KB of headroom at the end of P4 (31.28 of 35 KB). The sync engine and the sign-in and sign-out dialogs are lazy chunks; the initial chunk keeps only what decides whether to load them (`meta.userId`, a returning sign-in redirect). A guest never loads the sync engine. valibot stays on the server ([Architecture](architecture.md)).
   - **Acceptance:** API tests on a local D1; e2e "offline → online"; statistics stay visible while a batch is unacknowledged; a resent batch creates no duplicates; a delayed old batch is not applied; two-tab and two-device merge tests; two concurrent syncs lose no increments; an expired session resumes under the same `deviceId`, and signing in as another user never merges the previous user's data; a `400` stops retries until `appVersion` changes; a guest with 1,000 results signs in and all results arrive over several batches; sign-out and sign-in to the same account loses no data; one finished test writes at most 6 D1 rows, measured by meta.rows\_written; request CPU within the limit per `wrangler pages deployment tail`, in a cold and a warm isolate, for a learning sync and for a batch of 50 results on a `user_stats` row with a year of simulated learning on both tracks; property tests show that the set-like merges (learning entries, unlocked kana, recent answers, active days, typing records) are idempotent, commutative and associative and the additive ones commutative and associative; two devices learning the same track converge on unlocked kana, recent answers, boxes, active days and buckets; a sync that carries only learning progress writes at most 2 D1 rows; for any stored state and batch, the per-key patch of `learn_recent` and `learn_buckets` gives the same state as the full merge; a sync uses at most 50 D1 queries, whatever the size of the batch.

On Cloudflare a learning sync takes a warm median of 6 ms of CPU and writes 1 row, one finished test writes 5 rows, and the largest batch makes 7 D1 queries ([research note](../research/2026-11-19-p5-acceptance.md)). The bench project and its database were deleted after the phase (M6 of the plan).

The report dialog leaves with `/type`; `/api/reports` stays. Word and phrase chunks leave the web build until a phase uses them (words in P12), and `/about` credits only what is shipped; the content pipeline and its committed output stay.

   - The spec, `README.md`, `docs/architecture/` and the design system lose the typing trainer; the design export is updated from the artifact.
   - **Acceptance:** `/type` answers 404 with the static not-found page; no module, test, string or design component of typing is left, and `en` and `ru` keep key parity; `SCHEMA_VERSION` is raised, so a database of P5 is reset; a D1 migration drops `results` and the typing columns of `user_stats`, and `/api/sync` rejects a batch with typing data with `400`; a learning sync of a signed-in user still converges between two devices (the P5 e2e); `/stats` shows the learning section only; the render-isolation test and the latency test run on recall; the initial JS does not grow and every budget passes; no word or phrase chunk is in `dist/`.
   - **Closed** on 2026-11-20 by PR 6 of the [phase plan](../archive/p6-plan.md) (PRs 180–194). `/type` answers 404; the typing data left the client in sync format 2 and IndexedDB schema 5, and D1 in migrations `0002` and `0003`, checked on production by the maintainer; the browser tests and the latency gate run on recall ([ADR 095](../adr/095-remove-type-route-and-move-browser-tests-to-recall.md), [ADR 096](../adr/096-learning-only-data-and-sync-format-2.md)). The initial JavaScript went from 32.64 to 31.06 KB and the initial CSS from 8.83 to 7.64 KB ([Budgets and quality](quality.md), "End of P6").
8. **P7 — Knowledge model.**
   - Scope: a research note, then an ADR, then the model for kana in place of confidence and the Leitner boxes, with its sync. The research note:
     - takes its targets from [Learning goals](README.md#learning-goals);
     - simulates learners (a beginner, a learner who knows the kana, a learner who forgot them) against a reference memory model that none of the candidates uses (for example exponential forgetting with a different difficulty per item), so the comparison does not favour a candidate;
     - compares candidates for the memory state of an item (for example FSRS with default parameters), the weight of an answer by task type, answer time and hints, unlocking in groups by the recall probability of the items being learned, and the session planner (due reviews, weak items, new items; about 5 minutes a session);
     - defines one item model for kana and words, so later phases add items and task types without changing the stored state of a kana, and a word answer is evidence for each kana of the word;
     - decides how two devices merge the state (for example a replay of the merged answer log with older answers compacted into a snapshot, or the last state per item), proven by property tests that two devices converge.
   - The model accepts from the start every task type of ADR 093 and [ADR 099](../adr/099-learning-home-methods-and-phases-after-p6.md) (point 8):
     - recall, recognition, contrast, transfer, build, fluency run, listening, dictation and minimal pair;
     - answer features: correctness, answer time, a hint used, the lag in tasks since the kana was last seen, a re-check after an error, the wrong answer given;
     - a confusion count per ordered pair of kana, credit from a composite or a word to each kana in it, and links between the items of the two tracks (A7 as amended);
     - before a session starts: the forecast of the next unlock in sessions and an outline of the session; after it, what got stronger since the last session;
     - the threshold at which katakana is suggested next to hiragana.
   - The note measures how accurate the forecast of the next unlock is on the simulated learners.
   - The current screens get the smallest change the new state needs: confidence and the boxes go, and the chart states, the tooltip, the session summary and `/stats` follow the model. P7 adds no design.
   - The model is decided by [ADR 100](../adr/100-knowledge-model-fsrs-planner-and-answer-log.md): FSRS-6 with the A4 planner, grades by task type, katakana suggested once the 46 basic hiragana are learned, a forecast of the next row in sessions as a range, and an answer log synced as sync format 3. The current learning data are reset (ADR 061).
   - **Acceptance** ([ADR 100](../adr/100-knowledge-model-fsrs-planner-and-answer-log.md), point 10):
     - the model and the planner are pure TypeScript with injected time and randomness, and the FSRS-6 code matches ts-fsrs 6.0.0;
     - `packages/sim` runs on the production model; the reference beginner reads the 46 basic hiragana by day 8 with at least 90% review retention and at most 10 minutes a day (days 1–14), and the slow learners of part 3 stay within 2 points;
     - the state is a pure fold of the log, and property tests show that two devices converge whatever the order of delivery, duplicates and failed syncs;
     - every grade of ADR 100, point 4, has a test on synthetic answers;
     - a sync writes at most 3 rows as D1 counts them; `POST /api/sync` with a 256 KB batch stays within the CPU line of ADR 086; the sync e2e covers two devices, one of them offline for a while;
     - with a 4× CPU slowdown in Chromium, a fold of 40,000 answers takes at most 100 ms and a forecast at most 200 ms, outside keystroke handlers; the budgets and the latency test hold;
     - the forecast of the next row is off by at most 1 session (median) for the reference learner in the sim;
     - learning.md, metrics.md, storage-sync.md, backend.md and frontend.md describe the model, the log and the screens of P7.
9. **P8 — Learning home and progress.**
   - Scope ([ADR 099](../adr/099-learning-home-methods-and-phases-after-p6.md)): `/` is rewritten as a learning home driven by the model:
     - the next action with its reason;
     - the forecast of the next unlock in sessions;
     - the path through the groups of the track;
     - an outline of the next session;
     - what got stronger.
   - Hiragana is suggested first; the learner can switch the track. `/stats` becomes `/progress`, with the kana chart on top; "Leave session" and the summary return to `/`.
   - The session summary, the session screen, a kana details view and the navigation are redesigned with it. The design also draws the states of P9–P12 (stroke order, sound, first visit and placement, mnemonic, words the learner can read), which those phases turn on.
   - The design session in the design-system artifact and its export come before any code pull request.
10. **P9 — Learning methods.**
    - Scope ([ADR 099](../adr/099-learning-home-methods-and-phases-after-p6.md), [research note](../research/2026-11-21-kana-learning-methods.md)) as task types of the model:
      - contrast tasks for confusable kana, from the confusion state per pair;
      - feedback that teaches, with a re-check later in the session;
      - hiragana → katakana transfer;
      - building dakuten, handakuten and yōon from their parts;
      - fluency runs placed by the planner;
      - a stroke-order view in the details of every learnable kana. Its data comes from KanjiVG (CC BY-SA 3.0) or AnimCJK (LGPL), shipped as separate files under their licence and credited on `/about` and in `NOTICE.md`.
11. **P10 — Audio.**
    - The sound of every learnable kana is part of learning from its introduction ([ADR 093](../adr/093-learning-only-words-in-learning.md)): the source of the recordings (O6), the `sound` field of every learnable kana, the recordings, the file-based `AudioProvider`, the `learn.sound` setting, licence and credit on `/about`, and the task types of the model that use sound: listening (the sound is played, the learner picks the kana from 4), dictation (the learner types the romaji) and minimal pairs (か/が, は/ば/ぱ), all with one voice ([ADR 099](../adr/099-learning-home-methods-and-phases-after-p6.md)).
    - The source is open (O6) and its search runs alongside P7–P9. If O6 is not resolved when P9 closes, P11 goes first and P10 follows it.
    - **Acceptance:** every learnable kana of both scripts has a sound, and entries with the same pronunciation share a file; a learning session calls the provider after every task and on every task that uses sound, and never while `learn.sound` is off (fake provider); a sound that fails to load never delays the next task; no sound is part of the first load, and each file is at most 10 KB (`check-budget.mjs`); the sound plays after a key press in iOS Safari and Android Chrome (manual check recorded in the PR).
12. **P11 — Start.**
    - Scope: the first visit asks whether the learner knows kana. A learner who does takes an adaptive placement test by rows (a few timed recall tasks per row, stopping after rows the learner does not know), whose answers are evidence for the model and set the starting state; the test is available later from the progress screen. A beginner meets each kana with a mnemonic for its shape on the introduction task and in the kana's details. The mnemonics are written for the project in English and Russian with key parity, checked by the maintainer (O9), and shipped as a lazy chunk per language, not in the initial JS.
13. **P12 — Words in learning.**
    - Scope: tasks with words made only of kana the learner knows; each answer is evidence for every kana of the word; "words you can read now" on `/` and in the session summary; the report dialog on word tasks.
14. **P13 — Vocabulary.**
    - Scope: words learned with their English meanings as items of the model; the learner's vocabulary on the progress screen.
15. **P14 — Polish and release.**
    - Accessibility pass, device-matrix pass (including the input checks deferred from P2 and the kana sound), updated README and ARCHITECTURE, ADR entries, a stored-data description on `/about`, the release switch of the schema rule (below), release tag.
    - **Release switch** ([ADR 061](../adr/061-schema-reset-before-release.md), [Storage and sync](storage-sync.md#schema-changes)): `SCHEMA_VERSION` is set to 1; after the maintainer has opened the released build once, so that the development database is reset for the last time, a second commit sets `PRE_RELEASE` to `false`; the rule in `AGENTS.md` and the "Schema changes" section change to "migrations are mandatory"; a new ADR supersedes ADR 061.
    - **Acceptance:** Lighthouse ≥ 95 (median of 3 runs); manual pass on the device matrix recorded in the PR; keyboard-only pass through every screen, a learning session included; documentation matches the code; the release tag points at the deployed commit; a test fails when the number of IndexedDB migration steps differs from `SCHEMA_VERSION − 1`, and `PRE_RELEASE` is `false`.
