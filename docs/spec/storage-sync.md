# Storage and sync

All data is written to IndexedDB on the device first. Learning is a log of events; the server receives the device's own events as numbered batches, stores each as one row, and the device pulls the rows other devices wrote ([ADR 100](../adr/100-knowledge-model-fsrs-planner-and-answer-log.md), [ADR 102](../adr/102-sync-format-3-server.md)). The state is the fold of every event, so devices converge whatever the order and however many syncs failed. Sessions answered while offline arrive at the next sync.

## Local storage (D18)

Database `nekotype`, `meta.schemaVersion` = `SCHEMA_VERSION` (see "Schema changes"). The IndexedDB wrapper is promise-based, dependency-free, about 1 KB.

| Store       | Key           | Contents                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ----------- | ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `settings`  | `current`     | `Settings`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `outbox`    | `current`     | at most one batch awaiting acknowledgement: `{ seq, request }` (a `SyncRequest` of format 3)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| `forecasts` | `{row}@{day}` | the forecast history of this device ([Learning](learning.md#forecast)): a `ForecastRecord` per row and local day, `{ row, day, at, raw, started, actual }`; never synced, cleared with the log                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `log`       | key           | the learning log as pages of events (`LogPage`, [Backend](backend.md)): `own:open` (this device's open page, fewer than 500 events), `own:<n0>` (a closed own page, `n0` in 12 digits: 1, 501, 1001, …) and `row:<id>` (a row pulled from the server, as received). The state is never stored: it is the fold of these pages ([ADR 100](../adr/100-knowledge-model-fsrs-planner-and-answer-log.md), [ADR 103](../adr/103-log-on-the-client.md))                                                                                                                                                                                                                                                                        |
| `meta`      | key           | `deviceId`, `userId`, `lastSeq`, `schemaVersion`, `syncBlockedAtVersion`, `sessionExpired`, `settingsSyncedAt` (the `updatedAt` of the settings the server last acknowledged or sent), `profile` (`{ displayName, email, provider }`, for the account panel offline), `pendingSignIn` (`{ provider }`, written before the OAuth redirect), `keyIntervals` (the last 50 key intervals of recall answers, which give K; device-local, see [Metrics](metrics.md#learning-metrics)), `log` (`{ dev, next, lastAt }`: the log device id, the `n` of the next own event and the last own `at`), `sentN` (the highest own `n` the server acknowledged, 0 at first), `pulledId` (the highest server row id walked, 0 at first) |

- **Settings travel** in `SyncRequest.settings`, taken from the `settings` store when a batch is built (D16; [ADR 088](../adr/088-sync-engine-lazy-chunk-and-triggers.md)): the document goes if its `updatedAt` is greater than `meta.settingsSyncedAt`, otherwise `null`. After an acknowledgement or a pulled page, a local document that has not changed since the batch was built is replaced by the server's (`settingsSyncedAt` follows its `updatedAt`); one that has changed stays and goes with the next batch. An acknowledgement carries no settings, so the first batch of a sign-in is followed by a pull, which brings the account's settings.
- **Local view** = the fold of the log, own pages and pulled rows alike ([Learning](learning.md)). A batch does not move events anywhere: `meta.sentN` marks the own events the server acknowledged, and `outbox` holds the batch built and not yet acknowledged.
- **Compaction:** none in P7: the log keeps every event, about 2 MB a year; compaction comes back when a limit breaks ([ADR 100](../adr/100-knowledge-model-fsrs-planner-and-answer-log.md), point 7).
- **Legacy keys:** before the release nobody holds data worth carrying over ([ADR 061](../adr/061-schema-reset-before-release.md)), so nothing is migrated from `kanaflow:settings:v1` and `kanaflow:progress:v1`. Once IndexedDB has opened, the application deletes the legacy keys that the code no longer uses, without reading them: `kanaflow:settings:v1` from P3, `kanaflow:progress:v1` from P4 (`removeLegacyKeys()` in `shared/lib/storage`, called from `app/init.ts`). `nekotype:locale` stays in localStorage because the language is needed synchronously before the first render. A saved value that fails validation, including the removed `content: 'single'`, is replaced by its default.
- **Defaults:** `learn` = `{ strictness: 'learner', track: 'hiragana', targetMs: 1500, sound: true }`; `updatedAt` = 0.
- **Startup:** the application shell renders synchronously; a screen that needs the settings renders once `settings` has loaded.
- **IndexedDB unavailable** (blocked by the browser or failing to open): the application runs from memory for that page load and shows a notice that data will not be saved; the legacy keys are not deleted. A write that fails after the database opened (quota, a closed connection) switches the notice on for the rest of the page load; the state holds in memory.
- **Two tabs.** A store keeps the view it shows and the events it has not written yet. A write is one transaction that gives the events their `n` and `at` (see "The log"), so two tabs never share an `n`. After a successful write a tab posts on the `BroadcastChannel` `nekotype:learn` (`nekotype:settings`); a tab that receives the message applies the page to its fold, or reads the log again after a pull. Settings stay last-write-wins on the whole document. "Reset progress" (guests only) and the clearing of a sign-out post `reset` on `nekotype:learn`: the other tabs drop what they hold, events not yet written included.
- **The log (schema 6, P7).** An append is one `update` transaction that reads `meta.log` and `log/own:open`, gives each event `n = next++` and `at = max(at, lastAt)` and writes the open page and `meta.log` (a page that ends a block of 500 events is written under `own:<n0>` and the open page starts empty). Two tabs of a device share `dev`, and the transaction is what keeps their `n`s apart. Reading is `getAll('log')`, a page that fails its check skipped and repeated `(dev, n)` dropped; the fold orders the events. "Reset progress" (guests) clears the store `log` and the `meta` keys `log`, `sentN` and `pulledId`: a new log is a new device. The tabs tell each other on the channel `nekotype:learn`: `append` (the stored page), `pull` (rows were pulled) and `reset`; a tab applies an appended page to its fold, and folds again when an event arrives out of order. The local view is the fold of the log, with the current target answer time ([Learning](learning.md)).
- **The forecast history (schema 7, P8).** The store `forecasts` holds at most the newest 10 settled and 60 open records. It is read once with `getAll` when the first forecast is computed, held in memory and written through, never in a key handler; creating a record is an `update` transaction that writes only when the key is absent, so two tabs keep one. It is never synced. "Reset progress", sign-out, a discarded other account and account deletion clear it with the log (the tabs drop what they hold when `reset` arrives on `nekotype:learn`); the guest merge and a sign-in of the same user keep it, because they keep the log.
- **Hot path:** no IndexedDB writes inside a keystroke handler. A learning session writes after each answer, outside the handler: the action applies the event to the fold in memory and one write follows for a burst.

## Schema changes

- **Before the release (ADR 061, until the P14 release tag).** Nobody but the maintainer uses production, so a change to the IndexedDB schema resets the local data and no migration is written. `SCHEMA_VERSION` (an integer in `shared/lib`, next to `PRE_RELEASE`) grows in the pull request that changes a store or the format of its records, and each phase creates the stores it uses (schema 5, P6: `settings`, `delta`, `snapshot`, `outbox`, `meta`; schema 6, P7: `log` added, and `delta` and `snapshot` leave when the client moves to sync format 3; schema 7, P8: `forecasts` added; a device of an older schema is reset at its first start, with whatever it had not sent). `openDatabase()` opens the database without a version; when a store is missing, `meta.schemaVersion` differs from `SCHEMA_VERSION` or `meta` cannot be read, it closes the connection, deletes the database `nekotype`, creates it again at IndexedDB version 1 and writes `meta.schemaVersion`. This is silent (one `console.info` line). A failure to open, delete or create (blocked by another tab, refused by the browser) is the "IndexedDB unavailable" case: memory only, a notice, legacy keys kept. Another tab holding an old schema closes its connection on `versionchange`. `nekotype:locale` and the server are not reset.
- **After the release.** `SCHEMA_VERSION` starts at 1 and is the IndexedDB version. A change raises it and adds a migration step in `onupgradeneeded` with a test on a fixture of the previous version; `PRE_RELEASE` is `false` and a mismatch is never answered by a reset. A test fails when the number of migration steps differs from `SCHEMA_VERSION − 1`. The release switch is part of P14 ([Phases](phases.md)).

## Settings

```ts
type Settings = {
  learn: {
    strictness: Strictness;
    track: 'hiragana' | 'katakana';
    targetMs: number; // target answer time, good vs hard grade: 1000–3000 in steps of 250, default 1500
    sound: boolean; // play the kana sound after each task (P10), default true
  };
  updatedAt: number;
};
```

A stored document with any other key, the `typing` block of P5 among them, is not a valid `Settings`: it is replaced by the defaults, and the server rewrites the stored ones in migration `0002`. Settings are written to IndexedDB on each change, outside keystroke handlers; nothing waits for `pagehide`, because a transaction started there may not commit before the page unloads. `updatedAt` is set at each change.

The UI locale is device-local (`nekotype:locale`) and is not synced.

## Merge rules

The server merges nothing but settings: events are stored as received and never parsed into a state ([Backend](backend.md)). Every device builds the same state from the same events, by the order of the fold ([Learning](learning.md)).

| Data     | Rule                                                                                                                                                                                                                                   |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Settings | Last-write-wins on `updatedAt` for the whole document, except on a batch with `seq` = 1, which is the first batch of a new sign-in: if the account already has settings, the account settings win and the guest settings are discarded |
| Events   | A union by `(dev, n)`: an event received twice counts once; the order is `at`, then `dev`, then `n`                                                                                                                                    |
| Reports  | Sent separately via `POST /api/reports`                                                                                                                                                                                                |

## Batches

1. A new random `deviceId` is generated on every sign-in that starts from guest mode and stored in `meta` with `lastSeq` = 0. The server therefore never sees a reused `deviceId` with a reset `seq`, including after sign-out and sign-in to the same account. Renewing an expired session keeps them (see "Guest, sign-in and sign-out"). The `deviceId` of sync is not the `dev` of the log: `dev` belongs to the log and changes only when the log is cleared.
2. Sync runs under the Web Lock `nekotype-sync`, so only one tab of a device syncs at a time; all tabs share `deviceId`, the log and `outbox`.
3. If `outbox` holds an unacknowledged batch, it is resent unchanged. Otherwise a new batch is built with `seq = lastSeq + 1`, `after = meta.pulledId`, the changed settings and a log page: the longest prefix of the own events after `meta.sentN` whose request fits 256 KB (found by halving, at most 8,192 events). It is written to `outbox` in one transaction.
4. The server keeps the last applied `seq` and the time it was applied per `deviceId` (`device_seq`: `{ seq, at }`) and returns the `seq` in every sync response with `more`. `seq` ≤ last: not applied. `seq` = last + 1: applied atomically, one row per batch. `seq` > last + 1: `409` with the server's last `seq`; the client keeps its batch and resends it as last + 1.
5. On acknowledgement the client, in one transaction, sets `lastSeq` and `sentN` (the batch's last `n`), clears `outbox` and applies the settings rule. A pull follows when the answer says `more`, and after the first batch of a sign-in that carried settings. If own events are still unsent (the caps, or events that came after the batch was built), the next batch is sent 5 seconds later (the server's per-user interval), until none remain.
6. **The pull:** `GET /api/sync?deviceId=&after=<meta.pulledId>` answers the rows other devices wrote after `after`, a page at a time. The client repeats it until `more` is false. Each page is one transaction: its rows are stored in `log` as `row:<id>`, `meta.pulledId` is set to the page's `last`, and the settings rule applies. Afterwards the tabs read the log again. A page that fails its guard blocks syncing like a rejected batch.
7. Entries in `user_stats.device_seq` whose `at` is more than 90 days old are removed on the next write of that row.

## Sync triggers

- On application start, on network reconnect, and 10 seconds after a learning session ends. On start and on reconnect with nothing to send, the client pulls (Batches, step 6).
- On `visibilitychange: hidden`, via `fetch` with `keepalive`. Browsers limit keepalive request bodies to 64 KB, so the body MUST be at most 60 KB. The handler requests the Web Lock `nekotype-sync` with `ifAvailable`; if the lock is held by a running sync, nothing is sent. With the lock: if `outbox` holds a batch, that batch is resent unchanged when it fits in 60 KB, otherwise nothing is sent; if `outbox` is empty, a new batch is built by step 3 and sent only if it fits in 60 KB. The response is processed by step 5 if the page is still alive; otherwise the batch stays in `outbox` and the next regular trigger resends it.
- At most one request per 10 seconds per device, except for catch-up batches (step 5 above), which are spaced 5 seconds apart. A catch-up follows when own events are still unsent after an acknowledgement.
- A trigger with nothing to send does nothing, except the start and the reconnect (above). The engine runs only for a signed-in user (`meta.userId` set); a guest never loads it ([ADR 088](../adr/088-sync-engine-lazy-chunk-and-triggers.md)).

## Failed requests

In every case below the data stays in `outbox` and the log. Nothing is dropped automatically.

| Response                                                                        | Client behaviour                                                                                                                                                                                                      |
| ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Network error, `5xx`, D1 limit, a request cut off at the CPU limit (error 1102) | The next trigger retries. A `503` carrying `Retry-After` is handled like `429`                                                                                                                                        |
| `429`                                                                           | Wait for `Retry-After`, then retry (the engine sets a timer for the end of the wait, and the 10-second spacing still applies)                                                                                         |
| `409`                                                                           | Resend the batch as last + 1 (step 4)                                                                                                                                                                                 |
| `401`                                                                           | Set `meta.sessionExpired`, stop syncing, keep working locally and show "Sign in again"                                                                                                                                |
| `400`, `413`                                                                    | The batch cannot succeed unchanged. Store the current `appVersion` in `meta.syncBlockedAtVersion`, stop syncing and show the status. Retry only when `appVersion` differs, because a new release may accept the batch |

## Guest, sign-in and sign-out

- A guest accumulates events in the log from the first launch. On first sign-in the log stays and goes in the first batches (step 5); the account's other events arrive by the pull. Data from another device is combined, not overwritten.
- **Session state:** at start the client calls `GET /api/me` when `meta.userId` is set or a sign-in redirect has just returned, before the sync engine starts. A sign-in writes `meta.pendingSignIn` (`{ provider }`) before it leaves for the provider; its presence at the next start is what "has just returned" means, and the provider names the profile's `via` line and `sign in again` ([ADR 090](../adr/090-sign-in-sign-out-and-the-account-section.md)). A `401` follows the `401` rule above; it does not switch the application to guest mode or clear data, and it removes `pendingSignIn` (an abandoned sign-in leaves a guest a guest). No answer changes nothing: the next start asks again. A `200` for a guest is the guest merge: one transaction writes `userId`, a new `deviceId`, `lastSeq` = 0 and `profile`, and removes `pendingSignIn`.
- **Sign-in after an expired session,** compared with `meta.userId`:
  - Same user: `deviceId`, `lastSeq`, `outbox` and the log are kept and syncing resumes. Resending under the same `deviceId` keeps the batch idempotent.
  - Different user: the device holds another account's unsent data, which MUST NOT be merged into this account. If any is unsent, a dialog offers to cancel or to discard it. On discard, or if nothing is unsent, all user stores are cleared and the new user starts with no local data. On cancel, the new session is deleted through `POST /api/auth/logout` and `meta.sessionExpired` is set: the previous user's data stays for their next sign-in. While the dialog is open `/` stays in its loading state.
- **OAuth failure:** the callback redirects to `/?auth_error=denied` or `/?auth_error=failed`. The client shows a notice and removes the parameter from the URL.
- **Account deletion** clears all user stores after `DELETE /api/me` succeeds and returns to guest mode. It needs a connection and a valid session: offline, or with an expired session, the button is disabled and says why. While the request runs its dialog cannot be closed; a failure keeps everything and is shown in the dialog ([ADR 079](../adr/079-account-and-report-states.md)).
- **Reset progress** (A33) is available in guest mode only, after a confirmation dialog, and is not shown to a signed-in user, including one whose session has expired. It clears the log (see "The log"), which holds a guest's learning progress, and keeps `settings`.
- **Sign-out** needs a connection: offline it is not offered, because the session on the server could not be deleted ([ADR 079](../adr/079-account-and-report-states.md)). With an expired session it works without the server, which has no session left; the sync cannot run, so the unsent data is what the dialog names. Otherwise it first runs a sync. If unsent data remains (an `outbox`, or own events after `sentN`), a confirmation dialog states that some progress has not been sent and will be lost ([ADR 089](../adr/089-sign-out-text-and-dialog-fields.md)). The device is cleared only after `POST /api/auth/logout` answered; when it cannot be reached nothing changes. After sign-out all user stores on the device are cleared (`log`, `outbox` and `settings`; the settings return to their defaults), and so are the user keys of `meta`, including `deviceId`, `log`, `sentN` and `pulledId`; `schemaVersion` and `keyIntervals` stay. The application returns to guest mode.
