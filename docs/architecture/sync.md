# Sync on the client

The client side of [Storage and sync](../spec/storage-sync.md) and [backend.md](../spec/backend.md), since P5 PR 7 ([ADR 088](../adr/088-sync-engine-lazy-chunk-and-triggers.md)); sign-in, sign-out and the account section since PR 8 ([ADR 090](../adr/090-sign-in-sign-out-and-the-account-section.md)). The engine runs only while `meta.userId` is set.

## The engine (`model/engine.ts`)

`createSyncEngine(deps)` takes the database, the clock and scheduler, `fetch`, the locks, the page events, the channels (`learn`: the typed channel of `nekotype:learn`; `settings`: a `ChangeChannel`), `reloadLearning` and the callbacks to the user signals and to `requestSync`; the tests give it a fake server of format 4 that keeps one row per accepted batch (`model/test-util.ts`).

- **A cycle** runs under the lock `nekotype-sync`. It reads `meta`: no user, an expired session or a block at this `appVersion` end it (a block of another version is lifted). Then: an outbox in the database is resent unchanged; otherwise `buildNext` reads the own events after `meta.sentN` (`readUnsent`) and moves the next batch into the outbox in one `Db.update` (`lib/build-batch.ts`: the longest prefix of the unsent events whose request fits 256 KB, or 60 KB for the hidden page, found by halving; `after` = `meta.pulledId`; the settings when they changed). With nothing to send, `start` and `online` pull.
- **An acknowledgement** is one transaction: the outbox deleted, `meta.lastSeq` and `meta.sentN` (the batch's last `n`) written, and the settings rule applied (`lib/settings-after.ts`; the answer carries no settings, so a local document stays). A pull follows when the answer says `more`, or when the batch was the first of a sign-in and carried settings (the account's settings win on `seq` 1 and arrive with the pull). When own events are still unsent (the caps, or a session that ended while the batch waited) a catch-up batch follows 5 s later.
- **The pull** (`GET /api/sync?deviceId=&after=`, `lib/stored.ts` for the outbox guard) walks pages until `more` is false. Each page is one transaction: its rows stored as `log/row:<id>` as received, `meta.pulledId` = `last`, and the settings rule with the server's settings. When rows arrived, the engine calls `reloadLearning()` and posts `{ kind: 'pull' }` on `nekotype:learn`, so every tab folds the log again. A page that `readPullResponse` cannot read blocks syncing at this `appVersion`, as a rejected batch does. The local document, an outbox batch and a pulled page are read through `readSettings`, which drops the `learn.targetMs` of documents written before ADR 115.
- **Failures** follow the table of "Failed requests": a `409` rewrites the outbox's `seq` to `lastSeq + 1` and resends (three times at most per cycle); `401` writes `meta.sessionExpired` and calls `refreshUser`; `400` and `413` write `meta.syncBlockedAtVersion`; a `429` or a `503` with `Retry-After` sets `notBefore` and a timer; anything else leaves the data where it is.
- **Triggers:** `start` (at once, with a pull), `online` (with a pull), `requestSync` (10 s later, coalesced), `visibilitychange` to `hidden` (a `keepalive` request within 60 KB, only when the lock is free). Spacing: 10 s between requests, 5 s between catch-up batches.
- **Status** (`model/status.ts`, first match wins): `blocked`, `expired`, `offline`, `pending` (an outbox, own events after `sentN`, or settings newer than `settingsSyncedAt`), `synced`; it is computed from the database after each cycle and when `requestSync` is called, and shown by the account panel.

## Accounts (`model/account.ts`)

`createAccount(deps)` takes the database, the clock, `fetch`, the channels, `refreshUser`, `setSignInCheck` and the engine of the tab.

- **`check()`** calls `GET /api/me` and settles D19: `401` sets `sessionExpired` for a user and removes `pendingSignIn`; no answer changes nothing; `200` for a guest writes the new user's keys (a new `deviceId`, `lastSeq` = 0, the profile) and keeps the guest's log, whose events the first batches upload; `200` for the same user removes `sessionExpired` and keeps the device; `200` for another user clears the device when nothing of the previous account is unsent, and otherwise sets `signInCheck` to `choice` for the dialog.
- **`resolveAnotherAccount`**: `discard` clears the device and writes the new user's keys; `cancel` posts `POST /api/auth/logout` and sets `sessionExpired`.
- **Clearing** is one transaction over the user stores (`log`, `outbox`, `forecasts`, `settings`) and the user keys of `meta` (`log`, `sentN` and `pulledId` among them) (`schemaVersion` and `keyIntervals` stay), then `{ kind: 'reset' }` on `nekotype:learn` and `reset` on `nekotype:settings`; the settings store returns to its defaults when its document is gone.
- **Sign-out**: `prepareSignOut()` runs `engine.syncNow()` when the session is valid and returns whether anything is unsent (an outbox, or own events after `sentN`); `signOut()` posts the logout (not with an expired session), stops the engine and clears the device, or returns false and changes nothing when the server cannot be reached.
- **Account deletion**: `deleteAccount()` sends `DELETE /api/me`; only an answer of `204` counts. Then it stops the engine and clears the device exactly as sign-out does (the settings return to their defaults, Q3); any other answer, offline included, returns false and changes nothing. The button is disabled offline (`Needs a connection.`) and with an expired session (`Sign in again to delete the account.`).

The tests drive the account and the engine together on one fake server (`model/account.test.ts`): the guest merge, an expired session resumed under the same `deviceId` and `seq`, and sign-out followed by sign-in to the same account.

## The server, format 4 (`apps/api`)

The client sends format 4 only and the server accepts nothing else ([ADR 102](../adr/102-sync-format-3-server.md), [ADR 120](../adr/120-log-and-sync-format-4.md), [Backend](../spec/backend.md#sync-format-4)). The pieces:

- **`packages/shared/src/log-codec.ts`** is the one definition of a log page: `encodePage`, `decodePage` and `isLogPage` (the bounds of every event). An answer has 9, 10 or 11 fields, written in the shortest form, so a page of format 3 reads with `misses` 0 and no word. The client checks every page it reads with it and the server every batch.
- **`routes/sync.ts`** accepts `POST` with `v: 4` and `GET` with `after`; any other `v`, a `GET` without `after` and `part` are `400 invalid_body`.
- **`sync/apply-log.ts`** is the `seq` rule, the rate limit and the `device_seq` bookkeeping of a batch; **`db/batches.ts`** holds its SQL: the read of step 1, the guarded `batch()` of step 3 and the page of a pull, whose body is assembled from the stored texts.
- The table `sync_batches` (migration `0004`) has one `WITHOUT ROWID` row per batch; nothing in the API parses an event.
