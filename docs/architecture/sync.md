# Sync on the client

The client side of [Storage and sync](../spec/storage-sync.md) and [backend.md](../spec/backend.md), since P5 PR 7 ([ADR 088](../adr/088-sync-engine-lazy-chunk-and-triggers.md)); sign-in, sign-out and the account section since PR 8 ([ADR 090](../adr/090-sign-in-sign-out-and-the-account-section.md)). The engine runs only while `meta.userId` is set.

## The engine (`model/engine.ts`)

`createSyncEngine(deps)` takes the database, the clock and scheduler, `fetch`, the locks, the page events, one `ChangeChannel` per store and the callbacks to the user signals and to `requestSync`; the tests give it a fake server built from the shared merge functions (`model/test-util.ts`).

- **A cycle** runs under the lock `nekotype-sync`. It reads `meta`: no user, an expired session or a block at this `appVersion` end it (a block of another version is lifted). Then: an outbox in the database is resent unchanged; otherwise `buildNext` moves the next batch from `delta/learn`, `delta/typing`, the changed settings and up to 50 unsynced results into the outbox, in one `Db.update` (`lib/build-batch.ts`: `splitLearnDelta` with the caps, the 256 KB limit by dropping results from the end). With nothing to send, `start` and `online` call `GET /api/sync` and read the parts when the `version` differs.
- **An acknowledgement** with `version` = stored + 1 applies the batch to the snapshot with `applyBatch`; any other reads the three parts (twice at most again when their `version` values differ) and assembles the snapshot (`lib/apply-ack.ts`). One transaction writes the snapshot and `meta.snapshotVersion`, `meta.lastSeq`, deletes the outbox, marks the results `synced`, merges `records` with the server's when the snapshot was read, and applies the settings rule (`settingsAfter`). Then it posts on `nekotype:learn` and `nekotype:typing` (and `nekotype:settings` when it replaced the settings).
- **Failures** follow the table of "Failed requests": a `409` rewrites the outbox's `seq` to `lastSeq + 1` and resends (three times at most per cycle); `401` writes `meta.sessionExpired` and calls `refreshUser`; `400` and `413` write `meta.syncBlockedAtVersion`; a `429` or a `503` with `Retry-After` sets `notBefore` and a timer; anything else leaves the data where it is.
- **Triggers:** `start` (at once, with a pull), `online` (with a pull), `requestSync` (10 s later, coalesced), `visibilitychange` to `hidden` (a `keepalive` request within 60 KB, only when the lock is free, no results). Spacing: 10 s between requests, 5 s between catch-up batches.
- **Status** (`model/status.ts`, first match wins): `blocked`, `expired`, `offline`, `pending`, `synced`; it is computed from the database after each cycle and when `requestSync` is called, and shown by the account panel.
- **Retention** after an acknowledgement: above 1,000 results the oldest synced ones are deleted. Older results the history of `/stats` fetched (`loadOlderResults()` of `entities/stats`, `synced` = 1) are synced results like any other: the next retention removes the ones above the limit, and the page asks for them again when it is opened.

## Accounts (`model/account.ts`)

`createAccount(deps)` takes the database, the clock, `fetch`, the store channels, `refreshUser`, `setSignInCheck` and the engine of the tab.

- **`check()`** calls `GET /api/me` and settles D19: `401` sets `sessionExpired` for a user and removes `pendingSignIn`; no answer changes nothing; `200` for a guest writes the new user's keys (a new `deviceId`, `lastSeq` = 0, the profile); `200` for the same user removes `sessionExpired` and keeps the device; `200` for another user clears the device when nothing of the previous account is unsent, and otherwise sets `signInCheck` to `choice` for the dialog.
- **`resolveAnotherAccount`**: `discard` clears the device and writes the new user's keys; `cancel` posts `POST /api/auth/logout` and sets `sessionExpired`.
- **Clearing** is one transaction over the user stores and the user keys of `meta` (`schemaVersion` and `typingIntervals` stay), then `reset` on the three store channels; the settings store returns to its defaults when its document is gone.
- **Sign-out**: `prepareSignOut()` runs `engine.syncNow()` when the session is valid and returns what is unsent (`{ results, other }`); `signOut()` posts the logout (not with an expired session), stops the engine and clears the device, or returns false and changes nothing when the server cannot be reached.
- **Account deletion**: `deleteAccount()` sends `DELETE /api/me`; only an answer of `204` counts. Then it stops the engine and clears the device exactly as sign-out does (the settings return to their defaults, Q3); any other answer, offline included, returns false and changes nothing. The button is disabled offline (`Needs a connection.`) and with an expired session (`Sign in again to delete the account.`).

The tests drive the account and the engine together on one fake server (`model/account.test.ts`): the guest merge of 1,000 results over 20 batches, an expired session resumed under the same `deviceId` and `seq`, and sign-out followed by sign-in to the same account.
