# ADR 085: One Merge Function for the Learning State, a Tie Rule for the Personal Best, and a Delta Split by Caps

- **Context:** P5 PR 4 ([p5-plan.md](../../p5-plan.md), D11–D13) puts everything pure that the server and the client share into `packages/shared`. [ADR 078](078-user-stats-targeted-updates.md) and [ADR 082](082-sync-acknowledgement-without-snapshot.md) fix how the server reads and writes the learning columns per key; this record fixes the functions around them.
- **Decision:**
  1. **A delta is a state.** `LearnDelta` has the fields of `LearnState`, so `mergeLearn(a, b, order?)` is the only merge: a state with a delta (the server's stored row, the client's snapshot), a delta with a delta (compaction), a snapshot with an outbox. It uses the field rules of [storage-sync.md](../spec/storage-sync.md). `emptyLearnState()` is its neutral element.
  2. **Statistics.** `b` is the later side: a kana in both is `decay(add(a, b))`, a kana only in `b` is `decay(b)`, a kana only in `a` is copied as it is. A stored statistic can still be above 200 after one halving, so decaying a kana the batch did not touch would make the per-key patch differ from the full merge. The same rule is `mergeKanaStats` for typing.
  3. **The server's `unlocked`** is sorted by key (S5). Without `order`, `mergeLearn` sorts; the client passes the track order of its kana table.
  4. **The patches** are three functions over the touched keys only. `patchLearn` gives the merge patch of the small `learn` column: `unlocked` and `activeDays` whole, the changed `entries`, and the `stats` of the touched kana with `null` for each stored `mixups` key that the decay dropped. `patchRecent` gives the new list of each touched kana. `patchBuckets(storedDays, storedNewest, delta)` takes the stored newest day (`bucket_newest`, `null` for a track without a day) and returns the patch with the new newest day: the new buckets of the touched days and `null` for the days between the old and the new lower bound of the 365-day window, at most 366. Applied to the stored columns, each equals the part of `mergeLearn(stored, delta)`; property tests with a reference RFC 7396 merge keep them equal, including a removed `mixups` key and a gap of more than 365 days.
  5. **`applyBatch(snapshot, request)`** applies a batch to a snapshot with the full merge functions. The server writes the same result by patches; a property test keeps the two equal, which is what lets the client apply its own acknowledged batch ([ADR 082](082-sync-acknowledgement-without-snapshot.md), point 2). Settings follow the rule of the spec: last write wins on `updatedAt`, and on `seq` = 1 the account's settings win.
  6. **The tie rule (S7).** With equal KPM the personal best is the result with the smaller id. Before, the first result applied won, which depends on the order of application and made the records of two devices differ. `isBest` on the results screen stays "strictly higher than the best before", so nothing visible changes. `mergeTypingRecords` takes per key the better `best` and the union by `resultId` of `recent`, the 10 latest by `endedAt`, then id; `applyResultsToRecords` folds results sorted the same way.
  7. **Splitting.** `splitLearnDelta(delta, BATCH_CAPS)` takes into `head` the first 60 kana (entries, recent answers and statistics together, in key order) and the first 31 days of each track in ascending order, and all of `unlocked` and `activeDays`; the rest stays in the delta. The caps are those of Q1, confirmed by ADR 082. A statistic of one kana is on one side only, so nothing is decayed twice.
  8. **Shared constants and types.** `SYNC_FORMAT_VERSION` = 1, `MAX_RESULTS_PER_BATCH` = 50, `MAX_SYNC_BODY_BYTES` = 256 KB and `BATCH_CAPS` are in `shared/runtime`; the response types, `Snapshot`, its three parts and `ApiErrorCode` are in `shared/types`, with guards for what the client reads (`isSyncResponse`, `isSnapshot`, `isSnapshotRest`, `isSnapshotRecent`, `isSnapshotBuckets`). A track without a key in `bucket_newest` has no days.
- **Justification:** One function removes the chance that the client's view and the server's row follow different rules. Keeping the untouched side as it is makes the patch route and the full merge agree on any stored state, which is the precondition of the server reading only the keys of the batch. The tie rule is needed for the convergence of two devices; its only visible effect is which of two equal results is named as the best.
- **Consequences:**
  - Spec: [storage-sync.md](../spec/storage-sync.md) ("Merge rules", "Batches") and [metrics.md](../spec/metrics.md) (the personal best, `unlocked`) are changed in this pull request (S5, S7).
  - `apps/api` takes `ApiErrorCode` from `shared/types`; `apps/bench` calls the new `patchBuckets`.
  - Nothing imports the new functions yet, so the initial JS does not change; PR 5 and PR 6 start to use them.
- **Status:** In force. Extends [ADR 078](078-user-stats-targeted-updates.md) and [ADR 082](082-sync-acknowledgement-without-snapshot.md).
