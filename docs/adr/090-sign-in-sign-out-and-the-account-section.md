# ADR 090: Sign-In Returns Through `pendingSignIn`, Sign-Out Waits for the Server, and the Account Code Lives in the Sync Chunk

- **Status:** In force.
- **Context:** P5 PR 8 ([p5-plan.md](../archive/p5-plan.md), D19, D20, Q3) lets a user sign in, see the sync status, sign out and continue after an expired session. The plan fixes the flow; a few points it leaves open had to be settled in code, and the initial JavaScript grew past the allowance of D17.
- **Decision:**
  1. **The start.** `app/sync-bootstrap.ts` reads `auth_error` from the address, removes it with `history.replaceState` and keeps the notice until the next navigation. `initUser` reads `userId`, `sessionExpired`, `profile` and whether `pendingSignIn` is present. With a user or a pending sign-in it loads `features/sync` and awaits `checkAccount(db)` (`GET /api/me`, the four outcomes of D19) before the engine may start; the engine starts once a user is set and `signInCheck` is `idle`.
  2. **`signInCheck`** (`entities/user`): `checking` while a returning sign-in is checked, `choice` while the "another account" dialog waits, `idle` otherwise. `/` shows its loading state while it is not `idle`, so nothing of either account is shown before the choice (design decision 118). `App` renders the dialog from the sync chunk when it is `choice`.
  3. **No answer** from `GET /api/me` (network, `5xx`) changes nothing: `pendingSignIn` stays and the next start asks again. A `401` removes `pendingSignIn` in both cases of D19.
  4. **Cancel in the "another account" dialog** posts `POST /api/auth/logout` and sets `meta.sessionExpired`: the new session's cookie replaced the previous one, so the previous user's session is gone on this device too, and the previous user's data waits for their next sign-in.
  5. **Clearing a user** (sign-out, discard, another user with nothing unsent) is one transaction: the stores `results`, `delta`, `snapshot`, `outbox`, `records` and `settings` are cleared and the user keys of `meta` deleted; `schemaVersion` and `typingIntervals` stay. Then `reset` is posted on `nekotype:learn`, `nekotype:typing` and `nekotype:settings`; the settings store returns to its defaults when the document is gone (Q3).
  6. **Sign-out** with a valid session runs one sync cycle at once (`syncNow`, regardless of the 10-second spacing, never inside a `Retry-After` wait), then counts what is unsent (unsynced results; an outbox or a non-empty `delta`) and asks only when something is (ADR 089). It clears the device only after `POST /api/auth/logout` answered (`204`, or `401`: no session left); a network error or another status keeps everything and the button works again. With an expired session no request is made. The button is disabled when the engine knows the server is unreachable (`syncOnline`: the browser is offline or the last request failed on the network), except with an expired session.
  7. **Where the code is.** `entities/user` (initial) holds the signals, `initUser`, `refreshUser`, `beginSignIn` and the host list of D20; `meta.profile` is exposed unchecked (`storedProfile`) and parsed by `readProfile` of `features/sync`, read by the lazy account panel. `features/sync/model/account.ts` holds the account flows; `features/sync/ui/another-account-dialog.tsx` the dialog, whose strings are in the `settings` part of the dictionary, loaded with it. The profile's cat mark is `shared/ui/cat-mark.tsx`, a file of its own so that it stays in the panel's chunk.
  8. **Budget.** The allowance of PR 8 in D17 is raised from 0.4 KB to 0.8 KB (the maintainer, 18 November 2026): the initial JavaScript goes from 31.86 KB to 32.65 KB gzip. The phase cap of 33.5 KB stands; PR 10–12 add only lazy chunks.
- **Justification:**
  - _Awaiting the check before the engine starts._ With another account the engine would otherwise send the previous user's batch under the new session.
  - _Sign-out waits for the server._ ADR 079 offers sign-out only with a connection so that the session cannot outlive it; clearing the device after a failed request would leave exactly that.
  - _The budget._ What stays initial is needed at the start of every page load (the navigation link, the sign-in notice, the bootstrap of D19); moving it behind a further chunk would change D17 for about 0.1–0.2 KB.
