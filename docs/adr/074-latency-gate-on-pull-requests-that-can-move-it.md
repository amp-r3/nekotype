# ADR 074: The Latency Gate Runs on Pull Requests That Can Move It

- **Status:** In force. Amends [ADR 052](052-e2e-scope-and-latency-on-main.md): point 3 (the latency test runs on `main` and by hand, never on a pull request) is narrowed.
- **Context:** ADR 052 took the two-minute keystroke latency test off pull requests, so a regression showed only after the merge, on `main`, and stopped the deploy. It happened in P4: four content pull requests (#100–#103) were merged onto a red `main` because the recall probe had moved into a lazy chunk (the failure was `no probe`, fixed by #104), and none of them was deployed until then. A rule in the P4 plan, "run `e2e:latency` locally when a change touches lazy loading or the input source", depends on somebody remembering it.
- **Decision:**
  1. A pull request runs the latency gate (`pnpm run e2e:latency`, as on `main`) when it changes a file that can move keystroke latency or what the test measures through. The list is `LATENCY_PATHS` in `apps/web/scripts/latency-gate.mjs`: the input source, the training and learning code, the prompts and their lazy chunks, the dictionary parts, the shared UI, the application shell (lazy loading and prefetch), the engine, the latency test and its configuration, the Vite configuration, the lockfile and the workflows.
  2. The workflow checks out two commits of a pull request (its merge commit and the base) and a step runs `node apps/web/scripts/latency-gate.mjs HEAD^1 HEAD`, which writes `needed=true|false`. When the changed files cannot be listed it answers `true`.
  3. Pull requests that change only other files (the stats, about and settings screens, the stores, the content tooling, the shared package, documents) do not run it, as before. `main` and a manual run always run it, before anything is deployed, as before.
  4. A unit test (`apps/web/src/app/latency-gate.test.ts`, part of `verify:quick`) checks the matching, that every listed path exists, and that the workflow is wired to the script.
- **Justification:** The change moves the check to where it can block: the pull request. It costs about two minutes only on the pull requests that can break the property, which are a minority; the rest keep ADR 052's short wait. A list of paths is imprecise (a change outside it can still move latency), so `main` keeps the full gate as the backstop.
- **Consequences:** A pull request on the list takes about two minutes longer in CI (the job limit of 15 minutes stands). A new directory that can affect the hot path has to be added to `LATENCY_PATHS`; the test fails when a listed path no longer exists. The local rule of the P4 plan is no longer the only protection. The latency budgets and the ceilings are unchanged.
