# ADR 104: Learning on the Model: The Session on the Planner, Recording After the Key Handler, the Screens of P7

- **Status:** In force.
- **Context:** [ADR 100](100-knowledge-model-fsrs-planner-and-answer-log.md) replaces confidence, unlocking and the Leitner boxes with a model, and [ADR 103](103-log-on-the-client.md) built the log store on the client. P7 PR 9 moves `/`, the session and the summary onto them ([plan D17–D19](../archive/p7-plan.md), answers Q2–Q4) in the integration branch `p7-switch`. `/stats` and the sync stay on the old store until PRs 10 and 11, which is why its exports are renamed `legacy…` ([D21](../archive/p7-plan.md)).
- **Decision:**
  1. **The planner chooses each task when it is shown.** The session calls `nextTask(modelState(), { now, track, previous, rng })` from `start()`, the hold timer, and Enter, Space or a click after a wrong recognition choice; never from the key of a recall or an introduction. A session has `SESSION_TASKS` = 30 tasks and ends early at `null`. `mode`, `queue`, `REVIEW_TASKS`, `task-choice` and `review-queue` are gone; there is one kind of session and one primary `continue`.
  2. **Recording is deferred.** The handler that finishes a task finishes the view (the caret, the hold timer, the sound) and queues the record with `scheduler.setTimeout(…, 0)`. The callback calls `introduce` or `recordAnswer`; it runs before the hold timer, so the next task is planned on the answer, and it still runs when the learner leaves. A task's key handler does no fold, grade, lookup or IndexedDB call.
  3. **The wrong answer of a recall** is the kana the typed romaji matched: the accepted prefix plus the first rejected key, when that is exactly one spelling of exactly one kana of the task's track in the session's strictness (`spellingsFor`, one map per track and strictness); otherwise none. Only the first error counts, and Esc alone names none. Recognition records the option chosen and the time from showing the task to the choice; the options take their first distractor from the kana's confusions and fill with introduced kana first.
  4. **Both tracks in one session.** The planner reviews the due kana of both tracks and introduces from `settings.learn.track`; the options and the wrong answer of a task use the track of its kana.
  5. **Screens** ([D19](../archive/p7-plan.md)). The progress line is `mastered X of N` · streak · `due: n`, with `n` counting the due kana of both tracks and the part hidden at 0; the chart has locked, learning, learned and mastered cells, a due mark and "opens next" from the view; the details hold the confusions and the recognition accuracy; the summary lists `introduced`, `learned`, `faster`, `slower` and `confused`. The `confident` state is named `learned` in the code (`KanaChart` takes `learned`, class `is-st-learned`, the same fill). The design export is not redrawn; `docs/design/README.md` notes the difference until the design session of P8 ([Q2](../archive/p7-plan.md)).
  6. **The model is its own chunk.** `vite.config.ts` names the chunk of `packages/model/src` `model`; `check-budget.mjs` fails a build in which it is part of the initial chunk, is missing, or is a static import of a route chunk. The session runtime imports the planner from it; the learn store loads it by a dynamic import.
- **Consequences:** Until PR 11 the initial JavaScript holds both stores (the old one is not tree-shaken: it creates its store when the module loads): 32.15 KB gzip against 31.19 KB before the PR, 0.98 KB over, above the 0.5 KB of [plan D22](../archive/p7-plan.md). Built with the old store replaced by an empty stub it is 31.58 KB, which is what PR 11 returns to by deleting `model/store.ts` and the libraries only it uses (0.41 KB over the baseline of 31.17 KB, from the new store, the log and the chart's cells). Between PR 9 and PR 11 the sessions are recorded in the log only, so `/stats` shows nothing new and the three sync e2e tests that read its counters are marked `fixme`; PR 11 turns them back on ([plan D21](../archive/p7-plan.md)).
