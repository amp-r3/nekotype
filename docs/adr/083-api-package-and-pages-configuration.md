# ADR 083: The API Is a Workspace Package Mounted by a Root Functions Entry, Configured by a Root `wrangler.toml`, Migrated by CI and Tested in the Workers Runtime

- **Context:** P5 PR 2 ([p5-plan.md](../archive/p5-plan.md), D1–D5, D8, D22) puts the first server code into the repository: an empty API that is deployed, migrated and tested, so that the pull requests that follow only add routes. Four things had to be settled: where the code lives and how Pages finds it, where the project's configuration lives, how the D1 schema reaches the preview and production databases, and how the API is tested. Several items the plan listed as "not confirmed" were checked here.
- **Decision:**
  1. **Package and entry.** The code is `apps/api` (`@nekotype/api`, private, TypeScript source, no build step). `functions/api/[[route]].ts` at the repository root is one line that re-exports `onRequest` from `apps/api/src/pages-entry.ts`, which builds the Hono application with the real clock and `crypto.getRandomValues`. A test fails when the entry is anything but that line.
  2. **No `hono/cloudflare-pages`.** `onRequest` is a three-line adapter over `app.fetch(request, env, context)`. The adapter of Hono, `handle`, is marked deprecated ("will be removed in v5"), and the lint rule `no-deprecated` is on.
  3. **The application is a factory.** `createApp(deps)` returns `new Hono().basePath('/api')` with `onError`, `notFound`, the `Origin` check on every `POST`, `DELETE`, `PUT` and `PATCH` (a missing header is rejected) and a 256 KB body limit. `AppDeps` holds `clock` and `randomBytes`; the pull requests that need `oauth` and `verifyTurnstile` add them.
  4. **Configuration.** `wrangler.toml` at the repository root is the source of truth of the Pages project: top level for local development, `[env.preview]` and `[env.production]` with their own variables and D1 databases (`nekotype-preview` `50ed211b-…`, `nekotype` `b8a4a497-…`). Database ids are not secrets and are committed; secrets are not in the file. `wrangler` is a root `devDependency` at the version of the lockfile, and CI runs `pnpm exec wrangler` instead of `pnpm dlx wrangler@4`.
  5. **`_routes.json`** is `{ "version": 1, "include": ["/api/*"], "exclude": [] }` in `apps/web/public/`, so a static request never counts against the 100,000 Functions requests a day. The Vite dev server proxies `/api` to `http://localhost:8788`, where `pnpm run dev:api` serves the Functions on a local D1.
  6. **Migrations** are files `apps/api/migrations/NNNN_title.sql`. `0001_init.sql` is the schema of `backend.md` plus `users_email`. CI applies them with `wrangler d1 migrations apply DB --env <environment> --remote`: to the preview database before a preview deployment, and to production after the candidate's smoke test and before the production deploy. A merged migration is never edited and works with the code deployed before it.
  7. **API tests** run in the Workers runtime with `@cloudflare/vitest-plugin` (the successor of `@cloudflare/vitest-pool-workers`, which does not accept Vitest 5), on a Workers configuration of their own, `apps/api/wrangler.test.toml`, with no `main`. The migrations are read by `readD1Migrations` (exported from the package's entry, not from a `/config` path), passed in as a binding and applied once per test file by a setup file.
  8. **The smoke test** requests `/api/unknown` on every deployment and expects `404` with `{"error":{"code":"not_found"}}` as JSON: a deployment without its Functions bundle or without `_routes.json` answers the static 404 page and fails. The Functions of a new deployment go live a moment after its static files (the first CI run got the static 404 page on its first request and the JSON a minute later), so the check asks up to 10 times, 3 seconds apart, before it fails.
- **Justification:**
  - The plan's own layout (D1) keeps Hono out of the root package and lets one workspace package hold the server's code, its lint rules (`apps/web` and `@nekotype/engine` stay out) and its tests, as `architecture.md` lays out.
  - A manual migration step would be forgotten, and a deploy that needs a missing table fails for the user. `d1 migrations apply` records what it applied and takes a backup first. The cost is one more permission on the CI token (D1 — Edit).
  - The plugin runs the API's own code in `workerd`, so D1 behaves as on Cloudflare, including `batch()` and `meta`. The Node fallback of D8 (`getPlatformProxy`) was not needed.
- **Confirmed here** (of the plan's section 2): the test plugin runs with Vite 8 and Vitest 5 and a D1 binding, and without a `main`; `wrangler d1 migrations apply|list` accept `--env preview` with a Pages configuration, both with the binding name `DB` and the database name; `wrangler pages dev` at the repository root reads `wrangler.toml` and serves `functions/` with the local D1 and `pages_build_output_dir`. Confirmed by the CI run of this pull request: `wrangler pages deploy apps/web/dist` from the repository root uploads the Functions bundle and `_routes.json` (its log shows "Uploading Functions bundle"), and the preview answers `/api/unknown` with the JSON error body. The CI token's D1 permission works: "Apply D1 migrations (preview)" applied `0001_init.sql` to `nekotype-preview`.
- **Consequences:**
  - `wrangler` warns that `APP_ORIGIN` exists at the top level but not in `env.preview.vars`. That is intended: a preview leaves it unset and uses the origin of the request (D2).
  - Settings of the Pages project are changed in `wrangler.toml` only; a value set in the dashboard disappears with the first deploy that carries the file. The project had none (it was static).
  - Documents: `backend.md` (the index, the error codes `not_found` and `internal`, where migrations live), `architecture.md` and `quality.md` of the spec, `README.md`, `AGENTS.md`, `docs/architecture/`.
  - The lockfile and `vite.config.ts` change, so the keystroke latency gate runs on the pull request.
- **Status:** In force.
