# ADR 087: The Local View Is Snapshot, Outbox and Delta Merged; Every Write Is a Read-Modify-Write Transaction; Two Tabs Merge

- **Context:** P5 PR 6 ([p5-plan.md](../archive/p5-plan.md), D15, D18) prepares the client's data layer for sync. Until now `delta/learn` held the whole learning state and a tab wrote its state over the other tab's ("Two tabs before P5"). The spec says `delta` holds the changes since the last batch, and a signed-in device also holds a snapshot and an outbox.
- **Decision:**
  1. **Schema 4.** `SCHEMA_VERSION` is 4 and two stores are new: `snapshot` and `outbox`, both with the key `current` (S8). The local data resets once ([ADR 061](061-schema-reset-before-release.md)). The `meta` keys that sync adds (`settingsSyncedAt`, `profile`, `pendingSignIn`, S9, and those the spec already names) are written first in PR 7; the spec lists them now.
  2. **`delta` is a delta.** `delta/learn` is `{ learn: LearnDelta, counters }` and `delta/typing` is `{ kanaStats, counters }`: increments and changed entries since the last batch. For a guest, who never syncs, that is the whole state, so what a guest sees does not change.
  3. **The view** a store shows is `initial ⊕ snapshot ⊕ outbox ⊕ delta ⊕ unwritten`, merged by `mergeLearn` (learning) and `mergeKanaStats`, `addCounters` and `mergeTypingRecords` (typing), in the order the server sees them ([ADR 085](085-one-merge-function-tie-rule-and-split.md)). The typing records are the snapshot's merged with the device's own `records` record, which is idempotent, so a result that is in both counts once. The three stored sources are read in one transaction, so an acknowledgement, which moves the batch from `outbox` into `snapshot` in one transaction, is seen whole or not at all.
  4. **Incremental in an answer, whole on load.** An action applies its change to the view as before (the cost of one answer) and merges the same change, as a delta, into `unwritten`. The whole-state merge runs only when a store loads and when another tab posts. A helper, `unlockDelta`, turns what unlocking and box evaluation changed into a delta, so a re-evaluation is written like any other change.
  5. **`Db.update(reads, compute, scope?)`** reads records and writes what the synchronous `compute` returns in one `readwrite` transaction; `scope` names stores written but not read. A throwing `compute` or a write outside the declared stores aborts everything. Every read-modify-write goes through it: a store writes by merging its `unwritten` into the stored delta, `saveTest` reads `delta/typing` and `records` in the transaction that writes the result. `Db.getByIndex(store, index, value, limit)` serves the 50 unsynced results of PR 7. Both exist in the memory fallback with the same behaviour.
  6. **Two tabs merge.** A write no longer replaces the other tab's: it adds to what is stored. A message of another tab makes a store rebuild its view and put its own `unwritten` on top. "Reset progress" posts `reset` instead of `change`, and a tab that receives it drops its `unwritten` too. The channel message carries that kind; settings stay last-write-wins and ignore it.
  7. **The vowels are always unlocked.** The view starts from the initial state, so a stored delta cannot take them away; tests that seeded a state without them introduce the vowels instead.
  8. **A store checks the part it reads.** `readWithSyncBase` hands over the snapshot unchecked and the outbox's delta after a check of the batch envelope (`outboxDelta`: `seq`, `v`, `results`, `resultIds`). The learning store checks `learn` and `counters`, the typing store `kanaStats`, `counters` and `typingRecords`; a part that fails counts as absent, the other parts still count. The guards of the whole snapshot (`isSnapshot`, `isOutbox`) need the typing rules, which would then sit in the first screen's chunk.
- **Justification:** A delta that is the only copy of a guest's data and an increment for a signed-in user is one format. Merging on a message instead of overwriting is what lets two tabs of one device share one `delta` record, which the sync engine relies on when it moves the record into the outbox. Putting the read and the write in one transaction removes the lost update that a separate `get` and `put` allows between two tabs.
- **Consequences:**
  - Spec: [storage-sync.md](../spec/storage-sync.md) (the table, "Two tabs", S8) is changed in this pull request.
  - The merge functions, the stores' delta code and the two wrapper methods add 1.8 KB gzip to the initial JS. Three changes take back 1.5 KB of it (31.58 KB, 0.26 KB over the end of PR 5): the part checks of item 8; `packages/shared/src/runtime.ts` holds re-exports only (the settings guards moved to `settings-runtime.ts`), because a barrel with code of its own keeps every module it re-exports, with each export a lazy chunk uses, in the initial chunk; the memory fallback (`memory-db.ts`) is a chunk loaded only when IndexedDB cannot be opened.
  - `LATENCY_PATHS` lists `entities/learn/model/` and `shared/lib/idb/`, because recall is one of the three measured runs.
  - Nothing sends or receives yet; PR 7 adds the engine.
- **Status:** In force. Extends [ADR 072](072-delta-split-per-mode.md) and [ADR 082](082-sync-acknowledgement-without-snapshot.md). Amended by [ADR 096](096-learning-only-data-and-sync-format-2.md): the local database is schema 5, with one `delta` record (`learn`) and no `results` or `records` store.
