# ADR 097: CI Runs What a Change Can Reach, and `main` Does Not Repeat a Tree That Passed in Its Pull Request

- **Status:** In force. Amends [ADR 052](052-e2e-scope-and-latency-on-main.md): the latency test and the browser tests run on `main` unless the tree of the commit already passed them in its pull request. [ADR 074](074-latency-gate-on-pull-requests-that-can-move-it.md) and its list of paths are unchanged.
- **Context:** Every push to `main` ran the whole workflow again: `verify` with the browser tests (about 4 minutes), the latency test (49 seconds) and the deployment, about 6 minutes, although the same code had passed all of it in the pull request a minute before. A merge of Markdown files only waited just as long. Measured on CI (4 cores): install 30–40 s, typecheck + lint + format + docs 45 s, unit tests 47 s, build + budget 5 s, browser tests 57 s, sync tests 95 s, latency 49 s, deploy and smoke 35 s. The maintainer asked to cut the wait without checking less where a check is needed.
- **Decision:**
  1. **A scope job decides what a change needs** (`apps/web/scripts/ci-scope.mjs`, a whitelist; every other path, an empty list or a git error means everything runs). Changes to Markdown files only need Prettier and `docs:check` and nothing else: no test reads a `.md` file, and on `main` nothing is built or deployed (the bundle is the one in production). Changes to `apps/api` need the sync tests but not the Chromium and WebKit tests; changes to `apps/bench` and `packages/content` need neither (the web application depends on `engine` and `shared` only). `verify:quick` runs for every other change. On `main` the scope of the files does not apply, because `main` must hold a tree that passed everything.
  2. **A pull request records the tree it verified.** At the end of a successful run (checks the change needed, then the preview deployment) it uploads the artifact `verified-<git tree hash>` of the merge commit it checked out, kept 14 days.
  3. **`main` looks the tree of its commit up.** A squash merge gives the tree of the pull request's merge commit when `main` did not move since that run. If the artifact of a run of this repository (never a fork: `workflow_run.head_repository_id` is compared) exists and has not expired, `main` skips `verify:quick`, the browser tests, the sync tests and the latency test, and does what must happen for the deployment: install, build with the size budget again, the preview candidate, its smoke test, the production migrations, the production deployment and its smoke test. In every other case (a direct push, `workflow_dispatch`, another commit landed on `main` meanwhile, the artifact expired, the lookup failed) it runs everything, as before.
  4. The steps of CI are the steps of `verify` written one by one (`verify:quick`, the browser tests, the sync tests); a test keeps them equal to the scripts. The latency test, its list of paths and its rule for pull requests are unchanged.
- **Why not the alternatives:** Filtering the tests by package (`pnpm --filter "...[base]"`) misses files a test reads outside the package graph (`tokens.test.ts` reads `docs/design/source`). Caches of `tsc` and `eslint` save 15–25 s and can go stale. Parallel jobs shorten a pull request run, not a merge; they are a possible later step.
- **Consequences:** A merge of a pull request that passed takes install, build, deployment and smoke tests, about 1.5–2 minutes instead of 6; a merge of Markdown files does not deploy. The check on `main` is not weaker: a tree is skipped only when it is byte for byte a tree that passed the same checks. The first merge after this change shows whether GitHub's squash tree equals the merge-commit tree of the pull request run (step "Did this tree pass its pull request"); if it does not, `main` runs everything as before and a different key must be chosen. A second change landing on `main` between the run of a pull request and its merge costs one full run.
