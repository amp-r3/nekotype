# ADR 052: Browser Tests Off the Local Hot Path, Latency Gate on `main`

- **Status:** In force; point 3 is narrowed by [ADR 074](074-latency-gate-on-pull-requests-that-can-move-it.md) (a pull request that changes a file which can move latency runs the gate). Amends [ADR 045](045-e2e-on-production-bundle-and-gated-deploy.md) and [ADR 048](048-worst-keystroke-latency-gate.md) on where the browser tests run.
- **Context:** The browser tests were about three quarters of `verify`: in a CI run `verify` took 3:45, of which the unit tests took 24 s, the e2e on Chromium and WebKit 1:00 and the latency test 1:48. One change ran them up to three times: in the `pre-push` hook, in CI on the pull request and in CI on `main` after the merge. The project is in active development, and a push that waits for minutes of browser tests slows the work without adding a check that CI does not make.
- **Decision:**
  1. **`verify:quick`.** `verify` without the e2e: typecheck, lint, Prettier, unit tests with coverage, build and size budgets. The `pre-push` hook runs it. `verify` is `verify:quick` followed by `e2e`.
  2. **CI keeps the e2e.** `verify` runs the whole e2e suite on every push and pull request, as before.
  3. **The latency test moves to `main`.** `pnpm run e2e:latency` is a script of its own. CI runs it as a step after `verify`, on a push to `main` and on `workflow_dispatch`, before the deploy to `release-candidate`. A failure stops the workflow, so neither the candidate nor production receives the build. It does not run on pull requests.
  4. **Browser tests are written for what only a browser can show.** Focus, composition, layout and the engine of WebKit. Logic is tested without a browser (`docs/spec/frontend.md`, "Tests target behaviour").
- **Justification:** The browser tests check what the unit tests cannot, and CI is where that check is binding: a pull request cannot be merged by accident past it, and production cannot be deployed past it. Running it again on every push adds waiting and no safety. The latency test measures a property of the build, not of one change; it is enough that it gates what reaches users.
- **Consequences:** A regression in keystroke latency shows only after the merge, on `main`, and stops the deploy instead of the pull request; the fix is a new commit, as after a failed smoke test (ADR 045). A change that touches browser behaviour is checked by hand with `pnpm run e2e` or one file on Chromium, otherwise by CI. The pre-push hook no longer catches an e2e failure on the machine. If the latency test fails on `main` too often, it can return to pull requests behind a label.
