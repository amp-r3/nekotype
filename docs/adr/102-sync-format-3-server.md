# ADR 102: Sync Format 3 on the Server: One Guard for the Events, a Guarded Insert, Two Formats Side by Side

- **Status:** In force.
- **Context:** [ADR 100](100-knowledge-model-fsrs-planner-and-answer-log.md), point 7, replaces the deltas of sync format 2 with the log of answers, stored as one D1 row per batch. P7 PR 6 builds the server side ([plan D11–D15](../archive/p7-plan.md)) before the client moves, so the deployed client and server never disagree.
- **Decision:**
  1. **Two formats.** From PR 6 until PR 13 the server accepts format 2 and format 3: `POST` dispatches on `v`, `GET` on `after` (3) or `part` (2). `SYNC_FORMAT_VERSION` is 3, `SYNC_FORMAT_V2` is 2, and the format-2 types are `SyncRequestV2` and `SyncResponseV2`.
  2. **One guard for the events.** The bounds of a log page are `isLogPage` in `packages/shared/src/log-codec.ts`. The client needs a guard anyway (it never loads valibot), valibot was measured on batches of a few kilobytes while a 256 KB batch holds thousands of tuples, and one guard keeps the bounds in one place. The valibot schema of the request calls it through `v.custom`; the envelope stays a valibot schema. This amends [ADR 086](086-sync-endpoint-cpu-line.md), point 2, for the events only.
  3. **Rows.** A batch is one row of `sync_batches`, `WITHOUT ROWID`, so an insert writes one row; a sync writes at most 3 rows (`user_stats`, `sync_batches`, `user_settings`). Row ids are per user (`MAX(id) + 1`) and never reused while the account exists. The id is a scalar subquery in the select list of the insert: next to `WHERE EXISTS` as a `FROM` source it made a batch read every row of the user (measured in the [P7 sync note](../research/2026-11-23-p7-sync-endpoint.md)).
  4. **The insert is guarded by the `UPDATE`.** The plan guarded the insert with `version` = the version read plus one. That also holds when the `UPDATE` lost the race to a write that raised the version by one, so the lost attempt would add a row and its retry a second one. The guard also requires the stored `seq` of this device (`json_extract(device_seq, path)`) to be the batch's `seq`: only the request whose `UPDATE` applied has written it. The maintainer approved this change of D13. A test makes a competing write between the read and the write and counts one row.
  5. **The server never parses a batch** beyond the guard, and a pull page is put together from the stored texts.
- **Consequences:** The format-2 code stays until PR 13, which removes it with `SYNC_FORMAT_V2`. The CPU of a 256 KB batch is measured in PR 7 against the line of ADR 086; if the guard is too slow, the options are a smaller batch cap or a cheaper guard.
