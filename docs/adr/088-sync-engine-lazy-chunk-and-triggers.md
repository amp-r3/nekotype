# ADR 088: The Sync Engine Is a Lazy Chunk That Runs Only for a Signed-in User; It Works on IndexedDB and Tells the Stores Through Their Channels

- **Context:** P5 PR 7 ([p5-plan.md](../../p5-plan.md), D16, D17) adds the client side of the protocol of [ADR 082](082-sync-acknowledgement-without-snapshot.md) and [ADR 085](085-one-merge-function-tie-rule-and-split.md): batches, the outbox, the Web Lock, triggers, failed requests, catch-up and retention ([storage-sync.md](../spec/storage-sync.md)). A guest, who is nearly every user until sign-in exists (PR 8), must not pay for it: the initial JS has an allowance of 0.3 KB for this pull request.
- **Decision:**
  1. **One chunk, started by a user key.** `features/sync` is a dynamic import. `app/sync-bootstrap.ts` (initial chunk) reads `meta.userId` through `entities/user` and, once a user is set (at the start, or later when another tab posts on `nekotype:user`), imports the chunk and calls `startSync(db)`, which does nothing when the engine already runs. A guest loads nothing and makes no request. The engine starts only when `meta.userId` is set, and nothing sets it before PR 8.
  2. **The chunk is proved lazy by the budget script.** `check-budget.mjs` fails when the chunk of `src/features/sync/index.ts` is missing from the manifest, is the initial chunk, or is a static import of a route chunk (`src/pages/*/index.ts`, transitively). Only `pages/settings/ui/account-panel`, itself a lazy chunk loaded for a signed-in user, imports it statically. The idle prefetch fetches routes, so it never reaches it; an e2e test checks that a guest's page load, idle prefetch and a finished test make no request to `/api` and load neither chunk.
  3. **The engine works on IndexedDB and tells the stores to read again.** It never reads a store's memory. After a write that changes a view it posts on `nekotype:learn`, `nekotype:typing` and, when it replaced the settings, `nekotype:settings`; the stores of this tab receive the message through their own channel objects, as the other tabs do. A batch is built, and an acknowledgement stored, each in one `Db.update` transaction.
  4. **The lock.** Every cycle runs under the Web Lock `nekotype-sync`; without the API, under a mutex of the tab. The `hidden` trigger asks with `ifAvailable` and sends nothing when the lock is held.
  5. **Triggers and spacing.** `start` and `online` run at once and also check the server's `version` when nothing is to be sent; the end of a learning session or a typing test (`requestSync`, `shared/lib/idb/sync-request.ts`) runs 10 seconds later, several of them as one; `hidden` sends a `keepalive` request at once. At most one request per device in 10 seconds, catch-up batches 5 seconds apart. A timer that fires too early is set again for the remaining time.
  6. **Catch-up.** After an acknowledgement the next batch follows 5 seconds later when the batch just built left changes out because of the caps, or results remain unsynced. The engine remembers the first from the build, so a batch resent after a reload does not start a catch-up on its own; the next trigger sends what is left.
  7. **`Retry-After` is a timer.** [storage-sync.md](../spec/storage-sync.md) says a `429` or `503` waits for `Retry-After` and "the next trigger retries". The engine also sets a timer for the end of the wait, so that a batch does not sit until the next test or the next start; the 10-second spacing still applies after it. A network error or another `5xx` sets no timer and the next trigger retries.
  8. **The settings rule of D16** is one pure function, `settingsAfter`, used for an acknowledgement and for a snapshot read: a local document that has not changed since the batch was built is replaced by the server's and `settingsSyncedAt` follows it; one that has changed stays, with `settingsSyncedAt` below its `updatedAt`, so the next batch carries it.
  9. **Retention** runs after an acknowledgement: above 1,000 results the oldest synced ones go; an unsynced result never does.
  10. **Where things live (deviations from D17).** `requestSync` and `onSyncRequest` are in `shared/lib/idb/`, not `shared/lib/`: Steiger rejects a `shared/lib` of more than 15 modules, and the file is next to the other storage-side code. `entities/user` holds `userId`, `initUser` and `refreshUser` only; the `sessionExpired` and `profile` signals, which nothing outside the engine reads yet, come with PR 8 that shows them, because the allowance of this pull request is 0.3 KB and the pair costs about 0.1 KB.
- **Justification:** The user key as the only door keeps the cost of sync for a guest at the bootstrap (0.29 KB gzip). Working on the database and posting on the channels keeps one reader of each record per store and lets two tabs, or the engine and a store in one tab, never share memory. A pure settings function and a fake server built from the shared merge functions make the protocol testable without a browser.
- **Consequences:**
  - Spec: [storage-sync.md](../spec/storage-sync.md) ("Local storage", "Failed requests") and [quality.md](../spec/quality.md) are changed in this pull request; [architecture/sync.md](../architecture/sync.md) describes the code.
  - The initial JS grows from 31.59 KB to 31.88 KB. `LATENCY_PATHS` lists `app/sync-bootstrap.ts`.
  - PR 8 adds the session check, the guest merge, sign-out and the account section to the same chunk; it can start a second engine run through `startSync`.
- **Status:** In force. Extends [ADR 087](087-local-view-delta-accumulators-and-update-transactions.md).
