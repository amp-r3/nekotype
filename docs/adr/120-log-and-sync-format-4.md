# ADR 120: Log and Sync Format 4: Rejected Keys, the Word of an Event, Rules, the Shortest Encoding and Schema 8

- **Status:** In force.
- **Context:** The tasks of P9 need an answer log that says more than the one of [ADR 100](100-knowledge-model-fsrs-planner-and-answer-log.md), point 7. The grades of [ADR 117](117-grades-of-the-p9-task-types.md) tell a slip from an error by the number of rejected keys, a word is logged as one answer per kana, the rules of っ and ー have no memory but are logged, and two new task types exist. ADR 100 also reserved `hint` for a help that does not give the whole answer, which never existed, so Esc was logged as a rejected key only. [ADR 117](117-grades-of-the-p9-task-types.md), point 6, lists what the format adds; this decision fixes how it is written, read and moved to.
- **Decision:**
  1. **Two fields.** An answer holds `misses`, the keys rejected on it, 0–9 (more count as 9; 0 for a choice; a rule's rule errors), and `w`, the reading of the word it belongs to, at most 32 characters, or null outside a word task.
  2. **New values.** The task types `mismatch` and `script`. The rule keys `rule:sokuon` and `rule:choon`: the `k` of an introduction, or of an answer of task `word`, and nowhere else.
  3. **`hint` is a reveal.** It is set when the answer was revealed before it was typed (Esc, "show the romaji"), and such an answer is never `ok`. A reveal is not a rejected key, so it adds nothing to `misses`. An event of format 3 logged Esc as a rejected key and grades as before.
  4. **The shortest encoding.** An answer encodes as 9 fields when `misses` is 0 and `w` is null, 10 when only `w` is null, 11 otherwise. The decoder accepts the three; a missing field reads as 0 or null. An event of format 3 keeps its bytes.
  5. **One place for the bounds,** as before ([ADR 102](102-sync-format-3-server.md), point 2): `packages/shared/src/log-codec.ts`.
  6. **Sync format 4.** `SYNC_FORMAT_VERSION` is 4 and the server answers `400 invalid_body` to any other `v`, so a tab of older code stops syncing until it is reloaded (A28). A row of format 3 in D1 is a valid page, so pulls serve it as stored: no row is rewritten or dropped and there is no D1 migration.
  7. **IndexedDB schema 8, still a reset** ([ADR 061](061-schema-reset-before-release.md)). The log pages and the outbox change format, and a tab of older code would write over a page it cannot decode, so schema 7 cannot be kept. The reset deletes what a device has not sent. No code sends the old outbox first: before the release only the maintainer uses production, and the pull request is a draft until every signed-in device shows `synced`. Signing in again pulls the log back.
  8. **Until the grades of P9,** the fold ignores the events of a rule, as it ignores any key it has no item for, and `mismatch` and `script` have no effect on memory.
- **Justification:** A count of rejected keys is what the grades need and keeps the keys themselves out of the log. Leaving out trailing defaults costs nothing for the events that have none, which are most, and makes the old pages valid without a second decoder. A separate version for the old server path would have to be tested and removed again, for one user who can sync first.
- **Consequences:** A device that was not synced before the update loses what it had not sent. A tab left open on the old code gets `400` until a reload. The format changes in one step, so the fields no task writes yet (`w`, the new types, the rules) are bounded and tested before their producers exist.
