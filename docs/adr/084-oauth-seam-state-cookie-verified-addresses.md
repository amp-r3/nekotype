# ADR 084: OAuth Sits Behind a Provider Seam That Takes the Secrets per Call, the State Rides in One Short Cookie, and Only Verified Addresses Are Stored

- **Context:** P5 PR 3 ([p5-plan.md](../archive/p5-plan.md), D2, D6) adds sign-in with Google and GitHub, sessions and `GET /api/me`. The plan fixes the seam, the cookies and the linking rule; three details it left open had to be settled in code, and one rule of the spec (A4, "linked by verified email") needed a storage rule that keeps it safe.
- **Decision:**
  1. **The seam.** `AppDeps.oauth` is `Record<'google' | 'github', OAuthProvider>`. A provider has `authorizationUrl(credentials, state, codeVerifier, redirectUri): URL` and `profile(credentials, code, codeVerifier, redirectUri): Promise<OAuthProfile>`. `credentials` (`clientId`, `clientSecret`) is an argument, because a Pages Function receives its secrets with each request and not when the module loads; the signature in D2 had no place for them. `auth/providers.ts` implements the seam with Arctic; the API tests pass a fake; the Arctic-backed file has its own test with a stubbed global `fetch`.
  2. **State.** `GET /api/auth/:provider` draws the state and a PKCE verifier from `deps.randomBytes` (32 bytes each, base64url), sets `nt_oauth` = `<state>.<verifier>` (`HttpOnly; SameSite=Lax; Path=/api/auth; Max-Age=600`, plus `Secure` unless `APP_ORIGIN` is `http://…`) and redirects. GitHub ignores the verifier; the cookie has one format. The callback compares the state in the query with the cookie, and clears the cookie on every outcome.
  3. **Outcomes of the callback.** `error=access_denied` → `/?auth_error=denied`. A missing or different state, a missing code, a failed exchange or a failed profile request → `/?auth_error=failed`. Success → a session and `/`. A failure of D1 is not an OAuth failure and answers as everywhere else (`503 unavailable`).
  4. **Missing secrets.** A deployment without the client id or secret of a provider answers `503 unavailable` on `/api/auth/:provider` and its callback, the way the report endpoint does without its Turnstile secret (D21). The CI smoke test on production turns this into a failed deployment.
  5. **Preview.** With `ENVIRONMENT` = `preview` every route under `/api/auth/` answers `404 not_found`, logout included (S3); `/api/me` works and answers `401`.
  6. **Verified addresses only.** `users.email` holds a verified address in lower case or `NULL` (S2). A profile carries `email` only when the provider says it is verified (Google `email_verified`; GitHub's primary address with `verified`). Linking goes by `(provider, provider_user_id)`, then by `users.email`, else creates a user; because an unverified address is never stored, it can never link a later sign-in to someone else's account. A second sign-in method of an existing user does not change the stored name, avatar or address.
  7. **Sessions.** A 32-byte token (`deps.randomBytes`) in `nt_session`, its SHA-256 hex digest in `sessions.id_hash`; 30 days; a valid session with less than 15 days left is extended and the cookie is sent again; an expired row is deleted when it is seen (`401`); a sign-in deletes the user's other expired rows. Logout deletes the row and the cookie and answers `204` with or without a session.
  8. **The first `user_stats` row** is written with the user and its sign-in method in one `batch()`: the neutral values of D6, `bucket_newest` = `{}` and `last_sync_at` = 0.
- **Justification:**
  - Arctic reads the global `fetch`, which a test cannot replace without stubbing the platform, so the seam must sit above it (D2); secrets as an argument keep the seam stateless and the module free of request-time state.
  - The cookie is short-lived and scoped to `/api/auth`, so it is sent to no other request; an attacker cannot make a victim's browser finish a flow the attacker started, because the state the browser holds is not the one in the attacker's callback URL.
  - Storing only verified addresses is what makes email linking safe: an attacker who registers a GitHub account with someone else's unverified address gets a separate user.
- **Consequences:**
  - `Env` gains four optional secrets; `.dev.vars.example` lists them. The OAuth clients of M3 are needed for a real sign-in, never for the tests.
  - The smoke test checks `/api/me` (`401`) on every deployment and `/api/auth/google` (`302` to Google on production, `404` on a preview). Production's deployment has a hash address, so the workflow passes `--production` to the script instead of the script judging by the host.
  - `bucket_newest` = `{}` for a user with no buckets is a choice of this pull request: PR 4 and PR 5, which read it, must treat a track without a key as having no days.
- **Status:** In force.
