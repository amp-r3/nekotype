# ADR 098: CI Runs Its Checks in Parallel Jobs, and the Container Only Where a Browser Runs

- **Status:** In force. Amends [ADR 054](054-ci-in-the-playwright-image.md): only the jobs that start a browser run in the Playwright image. [ADR 052](052-e2e-scope-and-latency-on-main.md), [ADR 074](074-latency-gate-on-pull-requests-that-can-move-it.md) and [ADR 097](097-ci-scope-and-trees-verified-in-pull-requests.md) are unchanged in what runs; only where it runs changes.
- **Context:** After ADR 097 a pull request that reaches the application still took about 5 minutes 45 seconds, because one job ran every check one after another (run 44726742599): container 26 s, install 20 s, `verify:quick` 72 s, browser tests 57 s, sync tests 92 s, latency test 49 s, deployment and smoke test 13 s. None of these checks needs another: each Playwright configuration builds the bundle it tests (`dist-e2e`, `dist-e2e-sync`, `dist-probe`). The repository is public, so parallel runners cost nothing. The maintainer asked for a shorter pull request run with no test removed.
- **Decision:**
  1. **Six jobs.** `scope` (as in ADR 097, and now also the latency decision of `latency-gate.mjs`, exposed as the output `latency`) is followed by four jobs in parallel: `checks` (`verify:quick`, or Prettier and `docs:check` for Markdown only), `e2e-web` (Chromium and the `@mobile` tests on WebKit), `e2e-sync` and `latency`. `deploy` needs all five.
  2. **Each job keeps its condition from ADR 097.** A test job runs on `main` unless the tree is verified, and on a pull request when its files can reach it. `deploy` runs when `scope` succeeded and no job failed: a job skipped by scope or by a verified tree does not stop it, and a failed or cancelled one does. The preview deployment of a pull request waits for every test, as before, so the shared preview database receives no migration of an untested change. The artifact `verified-<tree>` is still uploaded last by `deploy`, so a failed check leaves none.
  3. **The container only where a browser runs.** `e2e-web`, `e2e-sync` and `latency` run in `mcr.microsoft.com/playwright:v<version>-noble`; `checks` and `deploy` run on the plain runner with `setup-node`, which saves the pull of the image. `ci-image.test.ts` checks the tag of every `container` block.
  4. **`deploy` builds again** (`pnpm run build && pnpm run budget`, about two seconds) instead of receiving `dist` as an artifact from `checks`.
  5. **The latency test has a runner to itself.** Before, it ran after the other tests in the same job; now no other process shares the CPU while it measures, so its numbers are no noisier than before.
  6. Each test job uploads the traces of a failed test under a name of its own (`playwright-test-results-web`, `-sync`, `-latency`): two artifacts of one run cannot share a name.
- **Why not the alternatives:** Running the checks as background processes inside one job would share four cores between browsers and the latency measurement. Sharding the browser tests across more jobs adds a container pull per shard for about 20 s of gain; the sync tests are the longest job. Letting the preview deploy start before the tests would show the preview earlier but would apply the migrations of an untested change to the shared preview database.
- **Consequences:** A pull request that reaches everything takes the longest test job (the sync tests: container, install, about 90 s) plus `deploy` (install, build, deployment, smoke test), about 3 minutes instead of 5:45. It uses more runner minutes in total (each job installs the dependencies), which is free for a public repository. A push to `main` with a verified tree skips the four check jobs and runs `deploy` alone, as in ADR 097. The steps of `verify` are still written one by one, now one per job; `app/ci-scope.test.ts` keeps them equal to the scripts.
