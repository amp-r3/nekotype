# ADR 096: Learning-Only Data: Settings Without `typing`, Flat Counters, IndexedDB Schema 5, Sync Format 2 and a Two-Step D1 Change

- **Status:** In force. Supersedes [ADR 072](072-delta-split-per-mode.md) (one `delta` record, not one per mode). Amends [ADR 095](095-remove-type-route-and-move-browser-tests-to-recall.md) (point 5: the latency gate's list no longer holds `entities/prompt/`), [ADR 078](078-user-stats-targeted-updates.md) and [ADR 082](082-sync-acknowledgement-without-snapshot.md) (the row of `user_stats` holds learning data only; the results history is gone) and [ADR 087](087-local-view-delta-accumulators-and-update-transactions.md) (the stores of the local database).
- **Context:** [ADR 093](093-learning-only-words-in-learning.md) removes the typing trainer, and [ADR 095](095-remove-type-route-and-move-browser-tests-to-recall.md) took its screen out of the code. What it saved is still in the shapes the client and the server exchange: the `typing` block of the settings, the counters per mode, the typing statistics, records and results of a batch, the stores `results` and `records`, the endpoint `GET /api/results`, and the table `results` and two columns of `user_stats` in D1. The pull request that removes them ([p6-plan.md](../archive/p6-plan.md), PR 4) changes formats that a P5 client and a P5 server also speak. Before the release only the maintainer syncs ([ADR 061](061-schema-reset-before-release.md)).
- **Decision:**
  1. **Settings** are `{ learn: { strictness, track, targetMs, sound }, updatedAt }`. The block keeps its name, because P8 and later phases add learning settings next to `sound`. The guard and the valibot schema are strict: a document with a `typing` block, or with any other key, is not valid. On a device the schema reset removes it; on the server migration `0002` removes `$.typing` from every stored document.
  2. **Counters** are `{ started, finished }`: learning sessions started and finished. `Mode` is gone. The same shape is in `delta/learn`, the snapshot, the batch and the D1 column `counters`.
  3. **IndexedDB schema 5.** The stores are `settings`, `delta`, `snapshot`, `outbox` and `meta`; `results` and `records` are gone, `delta` holds one record, `learn`, and the `BroadcastChannel` `nekotype:typing` with it. `meta.typingIntervals` is renamed `keyIntervals`, because it holds the key intervals that give K of the learning answer time. A P5 database is reset at the first start, and what the device had not sent is lost; the maintainer syncs before the merge (M2).
  4. **Sync format 2.** `SyncRequest = { v: 2, deviceId, seq, delta: { counters, learn, settings } }`; `Outbox = { seq, request }`; `Snapshot = { settings, counters, learn }`, and `GET /api/sync?part=rest` carries the same. The server accepts format 2 only: a body with `v: 1`, `results`, `kanaStats`, counters per mode or settings with a `typing` block is `400 invalid_body`. The old format is not accepted for a release, as the P5 plan foresaw for format changes before it: a P5 tab that is still open is blocked ([A28](../spec/decisions.md)) until it reloads, and the reload resets its `outbox`. `MAX_RESULTS_PER_BATCH`, the retention of results and the catch-up for results go; the catch-up of a delta over the caps stays. A batch that does not fit its byte limit is not built (the learning part is capped, so this does not happen in practice), where before results were dropped from the end.
  5. **`GET /api/results` is removed.** The path answers `404 not_found`. The history of `/stats` and `entities/stats` with it are gone. Sign-out with unsent data (`outbox` or `delta` not empty) names only that some progress has not been sent.
  6. **D1 in two steps.** A migration must work with the code deployed before it, and production is migrated before its deploy. So `0002_learning_only.sql` rewrites data and changes no schema: it removes `$.typing` from the settings, flattens the counters (`json_object('started', json_extract(counters, '$.started.learn'), …)`; every row has both modes, because the initial row wrote them), empties `kana_stats` and `typing_records` and deletes the rows of `results`. The server code of this change neither reads nor writes the three; only the insert of a new user still writes `'{}'` into the two `NOT NULL` columns. The table `results` and the two columns are dropped by the next pull request, after the maintainer has checked production (M3), with `0003_drop_typing.sql`.
  7. **The kana table and the binding of the engine to it** move from `entities/prompt` to `pages/learn/lib/prompt`: with `entities/stats` gone `pages/learn` is their only consumer, and `steiger` rejects a slice with one consumer (`fsd/insignificant-slice`, [ADR 015](015-merging-widgets-layer-into-pages-trainer-ui.md)). P10 gives words a home again. The generated chunks stay where the pipeline writes them, `entities/prompt/content/`, which `steiger` ignores as data without code; the latency gate's path list loses `entities/prompt/` and keeps `pages/learn/`.
  8. **The API of the database wrapper shrinks** with its last users: `getAll`, `count`, `getByIndex` and the indexes of a store go (they served `results`), and so does the reason of `requestSync`.
- **Justification:**
  - _A shape that nothing writes should not be accepted._ A strict schema is what makes a P5 client fail loudly instead of sending typing data that no one stores.
  - _Rewrite the data first, drop the schema later._ The deployed P5 code reads the typing columns; dropping them in the same deployment would fail every sync in between. Between the migration and the deploy (minutes) a P5 sync meets rewritten counters and is answered `500`; it retries, and only the maintainer syncs.
  - _No migration of the local database._ Before the release the schema reset is the rule (ADR 061); the data the reset loses is what the maintainer syncs first.
- **Consequences:**
  - The initial JS fell from 31.56 to 31.06 KB gzip and the initial CSS stayed at 7.77 KB.
  - A learning sync writes at most 2 rows and uses at most 13 of the 50 statements of D1; no Cloudflare measurement is needed, because the handler does less.
  - `apps/bench` is adapted minimally: its batches are the learning ones and its seed no longer writes typing data. Its Cloudflare project is deleted ([P5 plan](../archive/p5-plan.md), M6), so it is not run.
  - If D1 refuses `DROP COLUMN`, the next pull request rebuilds `user_stats` instead and records it in an ADR of its own.
