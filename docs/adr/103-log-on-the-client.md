# ADR 103: The Log on the Client: Pages in IndexedDB, Identity in the Transaction, a Lazy Model Chunk, Recording After the Key Handler

- **Status:** In force.
- **Context:** [ADR 100](100-knowledge-model-fsrs-planner-and-answer-log.md), point 7, makes the learning state a fold of an answer log. P7 PR 8 builds the client side of the log ([plan D16, D17](../archive/p7-plan.md)) in the integration branch `p7-switch`, before a screen uses it.
- **Decision:**
  1. **Pages in the store `log`** (schema 6): the open page of this device (`own:open`, fewer than `LOG_PAGE_EVENTS` events), closed own pages (`own:<first n of the block of 500>`) and pulled server rows (`row:<id>`), all stored as the `LogPage`s that travel. A record that fails `isLogPage` is skipped when read, as any invalid stored value is ([ADR 061](061-schema-reset-before-release.md)). The state is never stored.
  2. **Identity inside the transaction.** `appendEvents` reads `meta/log` (`dev`, next `n`, last `at`) and the open page, gives each draft `n = next++` and `at = max(draft.at, lastAt)` and writes both in one `update`. Two tabs of a device share `dev`; IndexedDB serializes their transactions, so they never share an `n`. A page closes when an event's `n` ends a block of 500, so the keys stay on the grid `1, 501, 1001, …` even when an unreadable open page was replaced.
  3. **The store folds in memory and writes later.** An action (`introduce`, `recordAnswer`, `startSession`, `endSession`) gives the event a provisional identity from its copy of `LogMeta`, applies it to the fold at once, publishes `describe(...)` and queues one write for a burst through the injected `Scheduler`. No action touches IndexedDB, so a keystroke handler never does. When the stored identity differs from the provisional one (another tab took the `n`), the store writes what is pending, reads the log again and folds it again. The same happens for an event out of order, a pull, and a changed target answer time (grades are folded with the current target).
  4. **The model is a lazy chunk.** `entities/learn` imports only types from `@nekotype/model`; `init` loads the log and `import('@nekotype/model')` in parallel and is `ready` when both are done, so the initial JS does not grow with the model.
  5. **A typed channel.** `nekotype:learn` carries `append` (the page just stored), `pull` and `reset`; `shared/lib` gets `typedChannel` with a guard, and the string channel of settings stays. The old store posts strings on the same name until PR 11 retires it; it takes any message for a change and reads its own record again, which is harmless, and this store drops what fails its guard.
  6. **Answer times are integers.** A recall time is rounded before it is stored: the guard of a page rejects a fraction, and a rejected page would lose its whole 500 events.
- **Consequences:** `delta` and `snapshot` stay in the schema until PR 11 drops them from `STORES` without raising the version again, because no build between PR 8 and PR 11 reaches `main` ([plan D21](../archive/p7-plan.md)). Clearing the log gives the next append a new `dev`: a new log is a new device for `(dev, n)`.
