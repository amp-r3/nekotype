# ADR 061: The Local Schema Resets Instead of Migrating Until the Release

- **Status:** In force until the P7 release tag, then superseded by a new ADR (see "Expiry"). Amends [ADR 025](025-rename-to-nekotype-and-new-pages-origin.md), [ADR 037](037-router-and-application-shell.md), [ADR 056](056-show-translation-setting.md) and [ADR 058](058-learning-first.md).
- **Context:** Until the end of P7 nobody but the maintainer uses `nekotype.pages.dev`, so there are no users, no saved data worth keeping and no old links. The spec still carried requirements that exist only for such users: a migration of `kanaflow:settings:v1` and `kanaflow:progress:v1` into IndexedDB with fixtures and an "interrupted migration" test, a 301 from `/learn`, a `single` → `words` conversion, an optional `showTranslation` kept so that saved values stay valid, and a rule that the keys change format only with a migration. The maintainer does not need the development progress kept between phases, nor an export and import tool.
- **Decision:**
  1. **No migration of the baseline data.** The legacy keys are deleted, not read: `kanaflow:settings:v1` from P3 and `kanaflow:progress:v1` from P4, by `removeLegacyKeys()` in `shared/lib/storage`, called from `app/init.ts` once IndexedDB has opened. If IndexedDB is unavailable they are kept. A saved value that fails validation is replaced by its default, so `content: 'single'` needs no conversion and `showTranslation` becomes a required field in P3.
  2. **No redirect from `/learn`.** The stub and its route are removed in P3; the path answers 404 like any unknown one.
  3. **Schema changes reset the local data.** Until the release no migration is written. `SCHEMA_VERSION` grows in the pull request that changes a store or the format of its records, and is stored in `meta.schemaVersion`. `openDatabase()` opens the database without a version. If a store is missing, `meta.schemaVersion` differs or `meta` cannot be read, it closes the connection, deletes the database `nekotype`, creates it again at IndexedDB version 1 and writes the version. The reset is silent (one `console.info` line). Each phase creates only the stores it uses.
  4. **Failure does not stop the application.** The open, delete and create steps are in a `try`/`catch`; a failure (blocked by another tab, refused by the browser) leaves the application running from memory with the existing notice, and the legacy keys are not deleted. A tab holding an old schema closes its connection on `versionchange`.
  5. **Not reset:** `nekotype:locale` and any server data.
  6. **Release version.** At the release the schema version is 1, as the IndexedDB version.
- **Justification:** A migration is code and a test written for data that nobody owns, and each later phase would add more of both. A reset costs the maintainer the development progress, which they accepted. Opening without a version avoids `VersionError` when the schema revision of the code goes down at the release. Alternatives rejected: an export and import tool for development data (not needed); keeping the migration "just in case" (it can only be tested against fixtures, never against real data).
- **Expiry:** The rule ends with the P7 release tag. The release switch ([Phases](../spec/phases.md), P7): `SCHEMA_VERSION` = 1; once the maintainer has opened the released build, so that the development database is reset for the last time, `PRE_RELEASE` (next to `SCHEMA_VERSION`) becomes `false`; from then on every schema change needs a migration step and a test, the rule in `AGENTS.md` and "Schema changes" in [Storage and sync](../spec/storage-sync.md#schema-changes) say so, and a new ADR supersedes this one. Sync, the merge rules, the guest merge, idempotent batches and account deletion are not affected: they work on the data of future users.
- **Consequences:** `storage-sync.md`, `phases.md` (P3, P4, P7 acceptance), `README.md` (D18, D25, D26), `decisions.md` (A39), `architecture.md`, `frontend.md`, `quality.md` and `AGENTS.md` lose the migration and the `/learn` redirect. In code, in P3: the `/learn` stub, the localStorage settings store and the optional `showTranslation` in `isSettings` go; in P4: the localStorage progress store, `isProgress` and the `a`/`m`/`t` type go. `README.md` and `docs/architecture/baseline-v1.md` change with the code of those phases.
